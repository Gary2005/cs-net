# cs-net-v5 3D 回放工作台 —— 用来看 `demo_extract` 到底提取出了什么

一句话：**把 `tools/demo_extract` 提取的数据用 3D 画出来，重点验证两件事 —— 逐 tick 提取对不对、真实烟雾体素和火焰格子长什么样。**

这是从 `cs-net/visualizer` copy 过来重写的版本。旧版依赖 `demo_parser`（0.25 s 一采）和一堆模型推理功能；
这里**只留 `demo_extract` 一条数据链**，模型相关功能全部删掉了。

---

## 1. 和旧版 cs-net visualizer 的差别（做了什么、删了什么）

| | cs-net（旧） | cs-net-v5（这个） |
|---|---|---|
| 数据提取 | `demo_parser`，固定 0.25 s 采样 | **`tools/demo_extract`**，默认**每 tick**（≈64 Hz），可切 4 Hz / 2 Hz / stride |
| 文件格式 | JSON / json.gz | **`.csz`**（demo_extract 自带列式二进制 + zstd，体积小 ~26×） |
| 下载按钮 | ⬇ JSON 压缩包（json.gz） | **⬇ `.csz`**（就是提取工具的原始格式，下载回来还是逐位相同的） |
| 烟雾 | **一个**半径硬编码 3.2 的静态半透明球 | **真实 32³ 体素云**：浏览器解码 Morton journal → 表面壳 → 填满表面点云凸包成实心云，逐体素 InstancedMesh |
| 火焰 | **一个**贴地 `CircleGeometry(2.6)` 圆盘 | **真实 16 格**：3D 坐标 + **表面法向** + 燃烧位，每格一片贴合表面的平面贴片 |
| 模型推理 | checkpoint 上传 / 路径预测 / spatial-only 胜率 / 低概率走位扫描 / 曲线弹窗 | 旧的 `demo_parser` 那条管线**全部删除**；现在另有一套：`app/ai` 用 `training/` 的训练产物直接对 `.csz` 推理，画成对枪弧线，五个头都在左下角的选手指标表里（见 §4.15） |
| 首屏 | 模型上传 + 设备选择 | **没有首屏了**：回放只能从 Demo 库进（见 §2） |
| 顶栏 | 自己的品牌块，没有导航 | 和 Demo 库 / 玩家页**共用一份**（`static/css/topbar.css`），从回放页能直接点回去。它在 `#app` **外面**，所以没有数据、显示「去 Demo 库」那一屏时顶栏和导航也还在 |
| 右面板 | AI 预测面板 | **数据检查面板**（提取元信息 / 本回合统计）；AI 的结果：视口顶部只有回合赢面 + 进度条，左下角是每个选手的五项概率，3D 里只有对枪弧线 |
| 比赛统计 | 无 | 右侧栏最上面的**「统计」弹窗**：每人的 K / D / A / K/D / ADR / KPR / 爆头率 / 伤害 / 承伤，加**每回合**的击杀、死亡、造成伤害、承受伤害（见 §3.5） |
| 可见性 | 无 | **选中一个玩家 → 他能看到的敌人头顶画眼睛**（`.csz` 的 `spotted` 列，见 §4.8） |
| 倍速 | 0.25×–4× | **0.1×**–4×（逐 tick 下看一两帧就过去的事件） |

保留的：Three.js 场景、OBJ 地图、OrbitControls 多相机、玩家模型/血条/轨迹、Minimap、
击杀信息、炸弹、投掷物轨迹、时间线、粒子背景、加载动画。

## 2. 快速开始

```bash
conda activate cs-net-v5          # 需要 demoparser2 / numpy / zstandard / flask

# 地图 OBJ：按顺序找 --maps-dir > <repo>/maps/optimized_obj_files
# > 隔壁 ../cs-net/maps/optimized_obj_files（cs-net-v5 里没有 maps/，所以现在用的是最后这个）。
# 想换成 cs-net-dev 的高精度地图（坐标系完全一样，只是面数 2.4 倍）：
python visualizer/server.py --host 127.0.0.1 --port 5000 \
    --maps-dir /path/to/cs-net-dev/maps/optimized_obj_files
```

启动后访问 `/api/maps` 可以看到实际生效的目录（返回里的 `dir` 字段）。
不要指向 `maps/obj_files` —— 那是未优化的原始导出，de_inferno 有 482 MB。

地图目录是**懒解析**的：启动时一个 `.obj` 都没找到（仓库里只带 `.obj.zip`），之后
每个请求会再找一遍，找到就记住。所以在库页面点完「解压地图」横幅之后，回放页刷新
一次就有建筑了，**不用重启 app**。`visualizer/tests/test_maps_api.py` 钉着这条。

打开 `http://127.0.0.1:5000/`。

**正常用法是从 Demo 库进**：完整应用 `python -m app.server --port 5000`，在
`/library` 勾选一场或多场 → 「载入分析」→ `/replay?batch=<id>`。回放页右上角的
下拉切换这一批里的哪一场，还没提取完的场次在下拉里是禁用的。

单独跑这个 server 时 `/` 就是回放页；没有 `?batch=` 也没有活着的会话，它会显示
一屏「去 Demo 库」的引导。**回放页没有上传界面** —— 以前有（拖拽 `.dem` / `.csz`、
浏览本机文件、选采样方式），已经删掉了：它和 Demo 库是两个入口，而 `.csz` 的采样
在提取时就定死了，在回放页再问一遍只会和库里的提取设置打架。

想直接用 API 加载一个本机文件还是可以的：

```bash
curl -X POST http://127.0.0.1:5000/api/load \
     -H 'Content-Type: application/json' \
     -d '{"path": "D:/demos/test.csz"}'
# 或者现场提取一个 .dem，顺便指定采样：
#   -d '{"path": "D:/demos/test.dem", "interval": 0.25}'
#   -d '{"path": "D:/demos/test.dem", "stride": 8}'
```

`.dem` 会走 `demo_extract.extract()` 现场提取，顺手写一份 `.csz` 到
`visualizer/outputs/`，之后 ⬇ 按钮下载的就是它；`.csz` 直接 `codec.load()` 读回。

实测（`test.dem`，110 MB，de_ancient，18 回合，101,293 tick）：

| 阶段 | 耗时 |
|---|---|
| `extract()` 每 tick（demoparser2 + Go side-channel 各读一遍） | **25.7 s** |
| `codec.save()`（zstd level 19） | **9.7 s** |
| `.csz` 体积 | **7.37 MB**（同一份数据的 JSON 约 183 MB） |
| 采样点 | **74,003 / 101,293 tick** |

提取是在后台线程里做的，页面会实时显示 `demo_extract.extract（every tick）…` → `解析完成（25.7s），正在写 .csz…`。

## 2.5 小地图：CS2 官方雷达图

小地图的底图不是自己画的，是**游戏自带的雷达图**：

| 文件 | 作用 |
|---|---|
| `panorama/images/overheadmaps/<map>_radar_psd.vtex_c` | 1024²、透明底、带 A/B 点格子和房间名 |
| `resource/overviews/<map>.txt` | `pos_x` / `pos_y` / `scale`，世界坐标 → 像素的变换 |

从 VPK 里抽出来、归位到 `visualizer/static/assets/radar/`（PNG + `map.json`）。
这些文件**已随仓库提交**，运行时不需要重新抽取：

```bash
visualizer/static/assets/radar/<map>_radar.png
visualizer/static/assets/radar/map.json
```

变换和游戏内雷达是同一个式子（`minimap-radar.js`、`app/radar.py` 都用它）：

```
col = (x - pos_x) / scale        row = (pos_y - y) / scale
```

也就是图左上角 = 世界 `(pos_x, pos_y)`，一像素 `scale` 个游戏单位。实测（mirage，100 万条
玩家轨迹）：**99.58%** 的采样点落在雷达的不透明像素上；`app/tests/test_radar.py` 用
inferno 跑到 **99.96%**，四个错误轴组合只有 16%–33%。

七个坑：

1. **相机朝向**。游戏内雷达是「屏幕右 = 世界 +x、屏幕上 = +y」，而 three 里
   `x=game y, z=game x`，所以小地图相机必须 `up=(1,0,0)`，取景框的 left/right 用 z、
   top/bottom 用 x。另外 `up` 必须在 `lookAt` **之前**设 —— 之后改不会重算四元数，
   原来那行 `up.set` 写在 `lookAt` 后面，其实一直没生效。
2. **多层地图**。nuke / train / vertigo 有上下两张雷达图，`verticalsections` 的
   `AltitudeMax` 是分界（nuke 是 -495），按玩家高度切；`map.json` 里存成
   `lower` + `lower_below_z`。
3. **`rotate` 字段**。dust2 的 overview 写着 `"rotate" "1"`，但导出的 vtex 已经是世界
   朝向，再转 90° 反而错位（用 100 万几何顶点验证过 0° 最优）。所以 `map.json` 不存
   这个字段，直接用图。
4. **贴图的 UV 要上下反着写**。`TextureLoader` 载入的贴图默认 `flipY = true`（上传 GPU
   时翻一次），所以 **v=1 才是图像顶行**。平面的 0/1 号角在 +x 侧（屏幕上方），要给
   v=1。写反了整张图上下颠倒：房间、楼梯全对不上，但 A/B 点和玩家标记还在原位，很
   容易误判成「转了个角度」而不是「翻了个面」。`scene.js` 里那两行 UV 有注释。
5. **玩家标记不走 WebGL，画在 2D 叠加层上**（`#minimap-overlay`，`drawMinimapMarkers`）。
   一开始它们和底图一样是 three 的网格，结果三件事同时出问题：雷达底图是
   `transparent: true`，渲染器把它排到所有不透明物体**之后**，不透明的箭头就被整片盖住，
   只在底图自身透明的地方漏出一点尖（「箭头若隐若现、但轨迹看得见」——轨迹是
   `opacity: 0.5` 的线，本来就在透明队列里）；形状只能是多边形，没有圆角/真描边，十几
   像素的箭头放大看全是锯齿；大小还跟着取景缩放走，全图视角下只剩 8px、拉近又变成
   30px 的大三角。搬到 2D 画布后层级就是 DOM 层级，大小按像素写死，描边和阴影随便调。
   投影仍然用同一个正交相机（屏幕右 = +z、上 = +x），所以位置和底图还是严丝合缝。
6. **标记的尺寸单位是 CSS 像素，不是画布像素**。角落小地图：箭头 14px、炸弹 7px
   （`MM_ARROW_CSS` / `MM_BOMB_CSS`），落笔前乘 `ui`（1 CSS px = 多少后备像素）。点开成
   2D 回放后换成另一档**固定尺寸**（箭头 10px、炸弹 5px，`MM_ARROW_2D_CSS` /
   `MM_BOMB_2D_CSS`），不再跟面板长度：那一档铺的是整张地图、面板又有 500px 以上，按
   √面积 放大出来的 20px 大三角会让 16 个人的箭头连成一片（这是前一版的做法，实测箭头
   21.9px，玩家密集时压成一块）。炸弹两档都刻意比箭头小一圈：它标的是一个点，老版本
   那个 15px 的红饼会把落点附近的玩家和掩体盖住。
7. **小地图和 3D 场景共用同一份 scene / 材质**。想让某个东西**只在小地图里**换个样子
   （现在只有「烟压暗」），只能在**小地图那一次绘制**期间临时改、画完立刻还原：
   `registerMinimapPass` 提供了这个前后钩子，`visuals.js` 用它把烟雾的体素 / sprite
   颜色乘暗（`MINIMAP_SMOKE_DIM`）。忘了还原的话 3D 视角里的烟也会跟着变深 —— 而那边
   的 `SMOKE_BASE_COLOR` 是逐像素和游戏比过的，动不得。

判断朝向**不要靠肉眼**：CDP 拍一张小地图帧 + 读同一时刻的 `minimapCamera.left/right/
top/bottom`，按相机参数反算出每个像素对应的世界坐标，再从雷达原图采样出 4 种候选朝向
（原样 / 上下翻 / 左右翻 / 180°）的参考图，算相关度取最大。修好前后 mirage 分别是
`flip-v +0.919` → `identity +0.965`（其余候选都在 ±0.10 以内），anubis `+0.988`、
inferno `+0.761`（该取景框有一角超出图外，被裁掉了）。

没有这批资产时会退回原来的「OBJ 俯视 + 高程灰阶」画法（`applyMinimapMapStyle`），
所以老 checkout 不会白屏。

### 2.5.1 点一下放大：2D 回放

点小地图（或 focus 之后按 Enter）= 把它放大成视口正中一块正方形；`Esc` / 再点一次 /
右上角 ✕ 都能收起。实现上**没有第二套渲染**：同一块画布、同一个正交相机，只是容器变大，
`syncMinimapCanvasSize()` 每帧把后备分辨率同步到显示尺寸（256 → 最多 1024，收起时降
回去）。CSS 那边 `.minimap-container.mm-expanded` 只负责定位和层级（压过曲线卡和指标表；
击杀播报例外地提到地图之上，2D 视野里也得看得见谁刚死），边长由 `main.js::layoutMinimap()`
按「视口短边 − 32」写成内联宽高，窗口尺寸变了会重算。3D 画面同时降到 `opacity: 0.16`
当背景 —— 露出旁边那块亮场景只会抢注意力。

这一档的取景**锁死成整张地图**，不跟着存活玩家缩放、也不平移（`scene.js::setMinimapMode2D`
+ `mapExtent()`：有雷达图就用雷达图那块矩形，没有就退回地图几何包围盒、算一次缓存）。
它是一块「回放」，位置关系要的是稳定参照 —— 跟着人动的话每换一个采样点整张图自己就挪
一下，反而看不清谁在往哪走。切档时 `mmSnapNext` 让第一帧直接落位，不做缓动；标记同时
换成小一号的固定尺寸，理由见上面第 6 条。

烟在小地图里另有一档更深的颜色（`visuals.js::MINIMAP_SMOKE_DIM`，线性 ×0.3 ≈ 肉眼亮度
×0.58）：俯视图里的烟是「0.14 不透明度的体素叠起来 + 一张发白的 sprite」，铺在雷达底图
上亮得像块白斑，A/B 点和房间名全被盖住。3D 视角里那个亮度是对的，所以只在小地图绘制
期间乘暗、画完立刻还原（第 7 条）。系数是逐档截图挑的：1 / 0.5 / 0.3 / 0.15 里 0.52 还
偏白、0.15 已经和地面糊成一块脏斑，0.3 既读得出是烟又不抢眼。

**箭头旁边写名字，点名字/箭头 = 点他左边那张卡。** 名字只在 2D 回放这一档画（角落那块
200px 上 10 个名字会糊成一片），11px、按队伍取箭头色的浅一档（CT `#cfe4f7` / T
`#ffd7a8`）+ 深色描边。位置**要避让**：一坨人挤在同一个房间时，全写右边会叠成一串
（"XANTARESJimpthat"），所以每个名字按「右 → 左 → 右上/右下 → 左上/左下 → 正上 → 正下」
依次试，取第一个不出画布、不压已放好的名字、也不压**任何**箭头的位置；实在挤不下才退回
右边那一档。避让的另一个好处是箭头不会被名字盖掉 —— 名字那 3px 深色描边压在过去会让
"箭头还在不在"都看不清。

点击是**两趟判定**（`scene.js::minimapPlayerAt`）：先按箭头圆找最近的（半径 = 0.75 ×
箭头长，最小 8px），没中就再看名字那一条矩形 —— 点名字和点箭头是一回事。点中 = 和点
左边卡片同一个动作（`togglePlayerDetail(idx, true)` + `focusCameraOnPlayer(idx)`：展开
详情卡、镜头飞过去并开始跟随），然后**把 2D 视图收起来**：镜头是在 3D 那边飞的，地图
开着的话你只能看着一块 0.16 透明度的背景，等于没跳。点空白处才是收起（和以前一样）。
鼠标移到箭头/名字上会变成小手（`pointermove` 里做同一套判定）。

> 顺带修了一个老 bug：`updatePlayerPanelFrame()` 每帧用 `card.className = 'player-card ct'`
> 整串覆盖，把 `togglePlayerDetail` 刚加上的 `expanded` 抹掉了 —— 所以卡片虽然展开了，
> 高亮描边和箭头翻转从来没显示过。现在覆盖时把 `expanded` 带过去。

测试：`node visualizer/tests/test_minimap_zoom.mjs <server-url> <match.csz>`。它会读
`#minimap-overlay` 的像素，量炸弹点的实际直径（不是只断言常量），验放大 / 收起 / 键盘 /
改窗口尺寸这几条路径；再验 2D 档的取景（取景宽度 = 雷达图宽度，且推进两秒后相机一动不动）；
验名字（每个箭头都有名字 + 按队伍色数到字的笔画）和点击（点箭头 / 点名字都会选中并收起，
点空白只收起不改选中）；最后切到烟雾最多的那个回合，把「小地图渲染那一刻」的烟雾材质颜色
抓出来，比「画时变暗、画完还原」（3D 场景那份不动）。

## 3. 怎么用这个工具测「新的数据提取」

### 3.1 换采样方式对比

采样方式**在提取时定**，所以对比要直接打 API（界面上那个下拉已经删了）：

```bash
curl -X POST http://127.0.0.1:5000/api/load \
     -H 'Content-Type: application/json' \
     -d '{"path": "D:/demos/test.dem", "interval": 0.25}'
```

| 选项 | 传给 `extract()` | 采样点（test.dem） | `.csz` |
|---|---|---|---|
| 每个 tick（默认） | 无 | 74,003 | 7.37 MB |
| 每 0.25 秒（4 Hz） | `interval=0.25` | 4,632 | ~0.93 MB |
| 每 0.5 秒（2 Hz） | `interval=0.5` | 2,322 | 0.56 MB |
| 每 8 个 tick | `stride=8` | 9,258 | 1.62 MB |

（四个数字都在本机实测：每 tick / stride=8 走完整 `extract()` + `codec.save()`；
2 Hz 那次是从 UI 全流程跑的，落盘在 `visualizer/outputs/test.csz`。
那次 UI 现在没了，但 `.csz` 还在。）

> 只对 `.dem` 生效。`.csz` 里已经是提取时定好的采样方式，读回来不会重采。

### 3.2 右侧「数据检查」面板

**提取结果**（来自 `data["meta"]` / `data["format"]`）：

```
格式            cs2.demo.v7
地图            de_ancient
tickrate        64
采样方式        every tick
采样点 / 总 tick 74,083 / 101,293     ← 该采的都采了
回合数          18
跳过回合        1（id 18）            ← 被跳过的回合不在 rounds 里，见 API.md §1.2
火焰实例        58
烟雾实例        82
火焰 / 烟雾数据  有（side-channel）
地面接触 on_ground 有（v6）
下蹲 crouch     有（v7）
spotted 可见性   有（逐 tick，谁看得见谁）   ← --no-spotted 提取的会写「无」
```

**本回合**：采样点、时长、tick 范围、当前采样/tick、本回合烟/火实例数、当前存活的烟/火、缺失采样数。

**玩家详情卡**（点左侧玩家卡片展开）额外验证 v6 / v7 新增的列：
`速度 v`、`地面 / 跳跃 / 落地`（`on_ground` / `jump` / `land`）、
`下蹲 / 眼高`（`crouch` / `crouching` / 眼高）、`开枪 / 脚步`（`shots` / `footsteps`）。
`on_ground` 就是 v6 相对 v5 多出来的 `CCSPlayerPawn.m_fFlags` bit0；
`crouch` 是 v7 多出来的 `m_flDuckAmount`，`crouching` 是同一个标志字的 bit2
（`FL_DUCKING`）。两者的区别见 API.md §4.12 —— **下蹲量是连续的斜坡，
碰撞盒是 72→54 的阶跃**，详情卡里两个数都写出来就是为了能当场对上。

### 3.3 拖时间线验证逐 tick 连续性

默认每 tick 采样时，时间线的 tick 间隔恒为 1/64 s，玩家位置在采样点之间线性插值 ——
拖动播放头应该完全平滑，不会有旧版 0.25 s 采样那种"跳一格"的感觉。

时间线支持两种操作：**点一下**跳过去、**按住拖动**实时跟手（`pointerdown` / `pointermove`
/ `pointerup`，指针被捕获，拖到时间线外面也继续跟）。按下时自动暂停播放 —— 否则
播放头和手指会抢同一个 `currentTime`。

#### 轨迹是采样点的纯函数（拖了时间轴不许变形）

`轨迹` 开关画的是每个选手**最近 150 个采样点**的尾迹，是 `visuals.js` 里的
`playerTrails`。它以前是一个"每帧往环形缓冲里 push 一个点"的累积器，而拖时间轴走的是
`seekTo()` —— 它只改 `currentSampleIdx`，一个点都不碰。于是跳转之后的第一帧把**跳转前**
和**跳转后**的位置连成一条横穿整张图的长线：

| de_inferno 实测（一个人） | 跳转前 | 来回拖 10 下之后 |
|---|---|---|
| 最长的一段 | 0.34 m（正常跑一步） | **37.9 m** |
| 整条轨迹长度 | 15.5 m | **279 m**（每拖一下还在涨） |

小地图渲染的是**同一个场景**（只是换成正交相机），所以两边一起坏 —— 表现就是
"拖进度条，3D 视图和小地图里的轨迹都在瞬移"。

现在按"采样点是否连续"分两路：连续 +1 就追加一个点（便宜），其余情况（跳转、倒退、
掉帧一次跳过好几个采样点、`轨迹` 开关关过一阵再打开、换回合）按历史**整条重算**。
两路都严格是"最近 150 个采样点、一个采样点一个点"，所以 `trail(k)` 只由采样点决定
—— 同一点永远是同一张轨迹。三个容易踩的点：

* 窗口里**不做"相邻两点太近就合并"**。滑窗贪心去重的相位取决于"从哪个采样点开始数"，
  于是一路播过来和跳过来会在同一段慢速移动上数出不同的点数（实测差 1 个点，整条轨迹
  的奇偶性错开一格）；合并带来的收益只是"站着不动时少几个重合点"，画面上本来就看不见
  （零长度的段画不出东西）。去掉之后两条路径逐点相同。
* 重算读的是**采样点上的原始位置**，不是 `getPlayerState()` 返回的插值结果。插值依赖
  `currentTime`，同一个采样点在不同播放相位能差几厘米；拿它重算，跳回来以后末端就对
  不上（看起来像"轨迹被抹了一下"）。
* 追加路径复用同一块 `Float32Array`（原来是每帧 `new BufferAttribute(...)` 重新分配），
  并关掉 `frustumCulled`：包围球是算一次就缓存的，几何体却每帧在变，参与视锥剔除会
  出现"镜头一转、整条轨迹消失"。

```bash
node visualizer/tests/test_trail_seek.mjs http://127.0.0.1:5099
# PASS: trail seek
```

测试量的全是**画出来的几何**（`__v5.trails` 直接读 `BufferGeometry` 里的点），参考值在
node 侧从原始采样点独立重算，不让被测代码给自己打分：播到位 → 跳走 → 跳回来必须逐点
相同；跳到任意采样点必须等于 `[k-149, k]` 的历史重算；任何一段都不能超过"正常每采样点
位移"；把 `轨迹` 开关关掉再打开同样成立；最后用 CDP 真的按住鼠标从 25% 拖到 85%，
再验一遍播放头位置和轨迹。

### 3.4 投掷物轨迹：一个投掷物 = 一条轨迹

投掷物点/轨迹按 `grenade_entity_id` 分组，**一个 eid 就是一次投掷**。

这里曾经有个 bug：分组键是 `thrower|type`（谁 + 什么道具），再用"和上一点距离
< 300 HU 就接上"的启发式切分。同一个玩家连丢两颗同类投掷物时，第二颗的起点常常
落在第一颗终点 300 HU 以内，于是两颗被并成一条轨迹 —— 表现是**第一颗落地后点不

### 3.5 「统计」弹窗：传统数据 / AI 数据两个页签

右侧栏**最上面**的 `📊 统计` 打开一个整页弹窗（✕ / 点遮罩 / Esc 都能关）。里面是
**两个页签**，共用一块内容区：

* **传统数据** —— `GET /api/stats`，服务端扫一遍内存里的整场 demo（`visualizer/stats.py`）。
  四块：本场合计（`K / D / A / +/- / K/D / ADR / KPR / 爆头率 / 伤害 / 承伤`）、
  **本场合计 · 细节**（首杀 / 首死 / 先手开枪 / 侧背身击杀 / 侧背身被击杀 / 穿烟击杀）、
  每回合四张矩阵（击杀 / 死亡 / 伤害 / 承伤）、**单回合明细**（上面那六列）。
* **AI 数据** —— `GET /api/ai/stats`，服务端逐回合跑模型（`app/ai/stats.py`）。
  本场平均五列 + 单回合明细。**切到这一页才发请求**：冷启动要逐回合跑模型
  （一场 17~24 个回合，实测 **2.5~5 分钟**），之后走磁盘缓存（几十毫秒）。
  这一页有自己的进度条（NDJSON 流，见 §3.5.3）。

**回合号在两处长得一模一样，点谁都是同一个动作**：回放跳到那一回合、弹窗不关、
矩阵的高亮列和下面的单回合明细一起换。整块弹窗里只有 `activeRoundIdx` 一个真相 ——
单回合明细没有自己的"选中回合"（早先这里是个 `<select>`，外加一项「跟当前回放」，
等于同一件事有两套状态，已删）。在弹窗里换回合还有一个副作用：`setRound()` 会把
播放停下来，所以关掉弹窗看到的是那一回合的开头。

表头上有个小 `?`：悬停显示这个数的**口径**（`visualizer/static/js/tips.js`，回放页和
玩家页共用同一份）。这些指标没有一个能"看名字就懂"—— 先手开枪要不要算没打中的枪、
侧背身按哪一帧判、穿烟用什么判据，都在解释里写死了。

**队伍怎么分**：半场会换边，所以不能按"第 1 回合站哪边"分。规则是
**任何一回合都没站在对面的两个人是队友**（和 `app/metadata.py` 算记分板同一条），
换边和只打了一半的替补都扛得住。队名只有"队伍 A / B" —— `.csz` 里没有真实队名，
表头写的是这一队**开场**站的边（`先 CT` / `先 T`）+ 比分。

**传统那四个数在服务端算**（算完缓存在会话里）。不逐回合拉载荷让浏览器自己加：
一个回合的载荷 100 KB~1 MB，24 个回合加起来几十 MB，而这份数据本来就在服务端内存里。

#### 3.5.1 五个新指标的口径

先定下「一场对枪」：**敌人之间的一次击杀**。自杀（`a == v`）、世界伤害致死
（`a == -1`）、队友击杀都不算 —— 没有对手，"谁先打谁"无从谈起；落在本回合采样范围
之外的也不收（`events` 是按「上一回合结束 → 本回合结束」分桶的，round 0 里混着赛前
热身的几十条击杀，见 `training_data/features.py::round_events`）。K / D 那几列沿用
老口径（和库里的记分板逐项相等），新指标不收热身。

于是每个选手每回合有四个分母。回放页的弹窗把这些比例显示成 `7/14`（分子 / 分母都在
格子里）；玩家档案页只显示百分比、样本数放在悬停里，首杀 / 首死在那里按回合数折算成
首杀率 / 首死率（见 `app/README.md` 的「数据统计」一节）：

| 指标 | 判据 | 分母 |
|---|---|---|
| **首杀 / 首死** | 本回合第一个造成 / 被造成对枪击杀的人 | —（一回合各一个） |
| **先手开枪占比** | 死亡前 4 秒内，两人之间**最早的那条伤害事件**是谁打的 | 参与的对枪数（击杀 + 被击杀） |
| **侧背身击杀** | 击杀者**第一次**打到受害者那一帧：受害者朝向 vs「受害者眼睛 → 击杀者眼睛」，水平夹角 **≥ 40°** | 击杀数 |
| **侧背身被击杀** | 同一件事的另一端（A 的侧背身击杀 +1 时，B 的侧背身被击杀 +1） | 被击杀数 |
| **穿烟击杀** | 受害者**死前最后一个活帧**，击杀者到他的连线被烟挡住（AI 的遮挡矩阵 `== 1`） | 击杀数 |

几条值得单独说：

* **「先手开枪」只认伤害事件**。"谁先"看的是伤害，不是开枪 —— demo 里没有可靠的
  开枪-命中对应关系（`shots` 列是逐 tick 的扳机状态，打空的枪不会产生 `player_hurt`）。
  所以"先手开枪"的实际含义是"这场对枪里先打到对面的人"。
* **侧背身的角度用水平面投影**：`forward = (cos yaw, sin yaw)`（Source 约定，yaw 从
  上方看逆时针增大），夹角用 `atan2(|叉积|, 点积)`，天然处理 ±180 的绕回。实测
  这个口径下"受害者最后一帧看向击杀者"的中位夹角是 **2°**、首枪时刻是 **5°**
  （4 份 demo 的 272 场对枪）—— 判据方向是对的，不是把前后左右搞反了。
* **穿烟用的是 AI 的逐帧遮挡矩阵**（`scripts/training_data/obstruction.py`，0 通 / 1 烟 /
  2 墙），取 `obstruction[a][v] == 1`。它和模型看到的是**同一段几何**，所以"面板说这是
  穿烟击杀"和"模型那一帧确实是隔着烟"永远是同一个事实。判据只是 2×2 的 `pair_matrix`
  （16 条射线而不是全场的 720 条），一帧 ~0.2 ms；一个回合只算有击杀的那几帧。
  **地图不认识 / 没装 numba 时整列降级**（`smoke_ok: false`，界面显示 `—`），
  其余指标照常 —— 传统统计不能因为一个可选列整块不可用。

实测（4 份 demo，传统统计这一侧）：

| demo | 对枪击杀 | 侧背身击杀 | 穿烟击杀 | 先手（占总对枪） |
|---|---|---|---|---|
| m1 anubis (17 回合) | 115 | 26 (22.6%) | 4 (3.5%) | 115 / 230 |
| m2 inferno (24) | 158 | 27 (17.1%) | 10 (6.3%) | 158 / 316 |
| m3 mirage (17) | 104 | 21 (20.2%) | 8 (7.7%) | 104 / 208 |
| m4 cache (20) | 122 | 19 (15.6%) | 4 (3.3%) | 122 / 244 |

恒等式（`test_stats.py` 里都是硬断言）：首杀合计 == 首死合计 == 回合数；侧背身击杀之和
== 侧背身被击杀之和；每场对枪恰好一个先手；侧背身 / 穿烟都是击杀的子集。

#### 3.5.2 AI 数据的五个数

全部来自**同一次**预测 —— 也就是回放页那条弧线和指标表用的那一批（`predict_round`
的载荷里多了个 `stats` 段，`CACHE_VERSION` 就是为它升上来的，现在是 5）。所以统计里的
胜率和画面上的弧线不会对不上。

设 `win_p[t]` = 选手 p 那一队在第 t 个采样点的胜率（`win_ct` 按他是 CT / T 折一下，
队伍未知时恒 0.5）：

| 指标 | 怎么算 |
|---|---|
| **平均击杀影响力** | 对每次击杀，`win_击杀者[后一个采样点] - win_击杀者[前一个采样点]`，再按击杀次数平均 |
| **平均回合影响力** | 逐采样点差分 CT 胜率（`d[k] = win[k+1] - win[k]`，末尾按真实胜负补 1 / 0），`d[k]` 记在**第 k 个采样点**的存活名单上按人数均分（CT `+d/x`、T `-d/y`），加总后按回合平均；某队全灭后沿用最后一个还有人活着的采样点。十个人加起来是 0 |
| **平均站位死亡风险** | 活着的每个采样点上 `next_death[自己]` 的平均（模型"下一个死的是谁"的逐帧概率） |
| **平均站位击杀率** | 同上，用 `next_kill[自己]` |
| **对枪评分** | 击杀：取「击杀前 2 秒」模型给击杀者赢的概率 p，分数 `1 - p`；被击杀：取同一时刻 p，分数 `-p`。最后 `(Σ击杀分数 + Σ被击杀分数) / (击杀次数 + 被击杀次数)` |

涨落记在"这一步开始时"那一帧的名单上 —— 所以在这一步里被打死的人也要承担这一步；
某一队全灭之后（炸弹已下、等拆包）沿用最后一个还有人活着的采样点，那几步的涨落照样
有人分。每回合十个人加起来严格是 0。

两个容易踩的坑，都写在代码里：

* **时间轴要对齐**。`predict_round` 手里的 `samples` 是**采样下标**（0, 16, 32…），
  而事件里的 `t` 是 **tick**（9808, 9824…）。当同一个轴用不会抛异常 —— 每次击杀都会
  落到"最后一个采样点之后"，影响力全变成 ±0.002 那种假数字。`build_round_stats`
  现在拿 `tensors.ticks[samples]` 当 tick 轴，`test_ai_stats.py` 用手算的用例钉死了它。
* **"后一个采样点"取第一个 `>= t` 的采样**：击杀那一 tick 的采样里受害者已经是死的
  （`alive` 就是 False），所以那一帧已经在"事后"了。击杀落在**最后一个采样点之后**
  （回合结束那一枪，实测 63% 的回合是这么结束的）时没有"后一个采样点"，
  按回合胜负补：赢了补 1.0、输了补 0.0 —— 需求里写的就是这条。

`对枪评分` 是唯一多出来的前向：每场对枪问两个方向（`(击杀者, 受害者)` 和
`(受害者, 击杀者)`），不做 `1 - p` 的翻转 —— 模型在两种朝向下不是严格互补的，
而训练集本来就是 50% 交换过的，两边都在分布内。一个回合 ~8 场对枪 ≈ 0.2 s。

#### 3.5.3 为什么 AI 那页要点一下才算

一整场 24 个回合 = 24 次特征构建（逐帧两两遮挡是大头）+ 24 次前向。实测（RTX 3090，
已经算过一遍 numba / 地图 BVH 之后）：

| demo | 回合 | 首次整场 | 之后（读磁盘缓存） |
|---|---|---|---|
| m1 anubis | 17 | 177 s | ~40 ms |
| m2 inferno | 24 | 314 s | ~40 ms |
| m3 mirage | 17 | 156 s | ~40 ms |
| m4 cache | 20 | 171 s | ~40 ms |

绝大多数人点「统计」只是想看 K/D/ADR，不该为此等五分钟。所以 AI 这一页是
**切到页签才发请求**，而且它走 `?progress=1` 的 NDJSON 流（一行一个事件：
`progress` / `result` / `error`），弹窗里画进度条 —— 关掉弹窗服务端也会把这场算完，
下次打开就是缓存。整场的汇总另外存一份 `<demo>/<models>_s16_match.json`，
和逐回合的载荷放在一起，删 `app/data/ai` 就一起没了。

`test_stats.py` 里有三类检查值得单独说：

* **换边的合成用例**：4 个人、3 回合、第 2 回合换边，还塞了自伤（`a == v`）、
  世界伤害（`a == -1`）、助攻、爆头、某回合完全无事件这几种边界。两边都错着"看起来
  也像对的"—— 比如自伤算进输出，数字只差一点点。
* **截断的护栏**：单回合单人承伤 ≤ 100、造成之和 + 世界伤害 == 承受之和。这两条就是
  "承伤 443" 那个 bug 的防线（真实文件里会逐格和面板对拍）。
* **新指标的手算用例**：另一场 4 人 / 1 回合的比赛，把"受害者朝 +Y、击杀者在 +X
  → 夹角 90° → 记一次侧背身"和"先手是受害者还是击杀者"逐条写死；还给了一条

##### ⚠️ 背景色是**状态**：透明段必须复位

**这个坑真出过一次，而且第一版测试全绿。** `\x1b[48;2;…m` 设的是状态，会一直留到被

现在 `test_banner.py` 里有一条**编码 → 解码的逐位对拍**：按终端的真实语义（先铺整格

## 4. 怎么用这个工具测「烟雾和火焰」

火焰和烟雾没有单独的检查区块了，直接在 3D 场景里看，用底部 `烟雾` / `火焰` /
`实心体素` / `烟雾贴图` / `火焰三层贴图` 开关控制显示。

底部开关：`轨迹` / `名称` / `选手 ID` / `烟雾` / `火焰` / `实心体素` / `碰撞盒 / 眼睛` / `瞄准射线` /
`子弹曳光` / `透视地图` / `选手 X 光` / `可见性（眼睛，实时几何）` / `视锥` /
`可见性角落射线`。

时间线中间的倍速下拉是 `0.1× / 0.25× / 0.5× / 1× / 2× / 4×`。**0.1× 是逐 tick 采样下
看细节用的**（64 Hz 的 demo 在 0.1× 时 1 秒真实时间只走 6.4 个 tick）——
曳光 / 脚步 / 下蹲这些一两帧就过去的事件，1× 下基本看不清。倍速只是
`advanceReplay()` 里乘在 dt 上，和采样方式、数据本身都无关。

### 4.1 火焰格子

* 数据来源：`rounds[i].fire[]`，每个 inferno（molotov / incendiary）一串**变更快照**。
* 每格有：`pos`（3D 世界坐标，Hammer unit）、`normal`（表面法向）、`parent`（蔓延树父格，未画）、`burning`（是否在烧）。
* 渲染：每格一片 `PlaneGeometry(1.35 m)` 的**贴片，躺在 `normal` 指的那个面上**（地面火就是平铺在地上的一滩），
  叠一层程序生成的径向渐变贴图 + 加色混合，相邻格自然连成一片；闪烁只做**水平胀缩**和整片亮度呼吸。
* 实测：`eid 1348 · incendiary`，11 个快照，最旺 **16 格**，包围盒 2.9 × 0.1 × 4.7 m——
  `y` 只有 0.1 m 说明这一把是**平地火**，所有格子同一高度。换一张有坡/箱子的火会看到 `y` 有跨度。
* 快照最后一帧 `burning` 全 `false`（tick 2202），之后自动不画 —— 这就是"火灭"。

> 为什么值得看：旧版火焰是**一个**贴地圆盘，完全看不出一把火有多少格、往哪蔓延、烧在哪个面上。
> 现在能直接看到 `m_firePositions` / `m_BurnNormal` 逐格的真实值。

> **为什么是平的不是柱子**：两场比赛（`test.dem` 58 处 + de_inferno 144 处，共 202 处火焰）逐格比对，
> 16 格坐标在整段燃烧里**一格都没动过**（每个下标只有 1 个不同坐标）；15,418 个燃烧格法向里
> 96% 的 `normal.y ≥ 0.9`（中位数 ≈ 1.000），只有 3~4% 是明显倾斜的。
> 也就是说这 16 格本来就是**表面上的燃烧点**，火是一滩铺开的；早期版本按法向立锥体，
> 视觉上就成了 16 根"地刺"。火势蔓延体现在"哪些格在烧"（实测 1→2→3→5→6→8→10→12→14→16 格），
> 贴片逐格出现即可。

### 4.2 烟雾体素

* 数据来源：`rounds[i].smoke[]`，每个烟雾一串 **journal 变更记录**（`append` / `full` + base64 字节）。
* 浏览器端 `static/js/smoke-voxels.js` 把它解回几何：
  1. 按变更序号**折叠**出该 tick 的完整 journal 字节；
  2. 解析 KEYFRAME / DELTA / HEARTBEAT 记录；
  3. Morton 解码 → **边界体素**（云表面）；
  4. 表面采样很稀（见下），于是**填满表面点云的凸包** → **实心云**；
  5. `world = detonation + (grid − 15.5) × 12.0`（HU）→ three 坐标。
* 渲染：逐体素 `InstancedMesh`，体素边长 12 HU = 0.3048 m，半透明材质、不写深度，
  大量体素叠加出体积感。`实心体素` 关掉 = 只画边界壳（`solidFromShell` vs `boundaryGrid`）。
* 实测日志规模：201 条 journal 记录 = 1 个 keyframe + 21 个 delta + 179 个 heartbeat；
  解出来的边界 1618、凸包实心 4207 个体素。
* 实测一轮：`eid 1352` 在 tick 2115（detonate）开始有数据，到 tick 3522（≈expire）停止；
  包围盒 **8.8 × 3.4 × 5.8 m** —— CS2 烟雾直径就是 ~7 m 量级，对得上。

> **为什么要填凸包，而不是洪泛填充**：journal 里的掩码是云的**表面**，而且采样得很稀 ——
> 真实 demo 上平均每列只有 ~4 个 Z（83% 的列是**一段**连续的 Z），没有任何一个格子的 64 位全满。
> 结果是六个外表面的洪泛填充**一个内部体素都补不出来**（`test.dem` 82 个烟里 59 个增益为 0，
> 最大也只有 20）。只画边界壳就会看到"两边高、中间空"的破形状 —— 也就是早期版本那个问题。
> 凸包的好处是**不需要任何参数**：凸体的竖直截面一定是一个区间，所以"填满凸包"就等于
> 逐列填满，而每列的上下界由凸包自己插值出来，稀疏采样之间的洞会被自动补上。
> `eid 1352` 的轮廓填充率从 **0.68~0.80 → 0.81~0.84**。
> 这条洪泛填充路径**试过、也删掉了** —— 它在真实数据上退化成边界，留着只会让人以为还有第二条重建路线。

> ### 🎨 这两套画法都**只影响画面**，不改动任何数据文件
>
> `solidFromShell` / `convexHullFillGrid` / `boundaryGrid` 全部是**读取端**的渲染代码：
> 它们只在浏览器里把 journal 字节变成几何，**不参与 `.csz` 的读写**。切换 `实心体素`
> 开关、甚至删掉整个 `solidFromShell`，`.csz` 的字节都不会有任何变化 ——
> 文件里存的始终是原始 journal 与真实火焰格子。

> ### ⚠️ 哪部分是"数据"，哪部分是"我猜的"
>
> 这个区分很重要，别把重建值当成提取结果：
>
> | 层 | 出处 | 性质 |
> |---|---|---|
> | journal 格式、两级 Morton 解码、`world = detonation + (grid−15.5)×12` | 社区逆向（`CS2-insight-agent` 的 `smoke_voxel_decode.py`），我们逐位对齐并有测试守着 | **可信**（但不是 Valve 官方文档） |
> | 洪泛填充 `occupied \| (MASK ^ outside)` | 参考实现里本来就有（`_rebuild_occupied_grid`） | 参考实现的做法，但在真实数据上退化成边界，**本项目已弃用并删除** |
> | **填满表面点云的凸包**（`solid_from_shell` / `convexHullFillGrid`） | **本项目自己加的渲染启发式** | **⚠️ 不是官方，也不在参考实现里。好处是没有可调参数，代价是它假设烟雾是凸的 —— 真实的凹陷会被一并填平** |
>
> 参考实现自己也没做 3D 实心体：它的 `project_smoke_grid_to_cells` 虽然调了洪泛填充，
> 但**只取每列的 `min_z` / `max_z` 两个点**，docstring 写的是喂给 **2D 雷达轮廓**用的
> （*"so multi-level radar filtering can select the appropriate layer before contouring"*）。
> 也就是说"这 32³ 该不该是实心"这个问题，参考实现是**绕过去的**，没有回答。
>
> 所以：解码层可信、可验证；**"实心云"是渲染层为了好看做的重建**。
> 我们没能 100% 排除"存在第三种解码方式能直接解出实心体"，也没找到 Valve 或社区
> 对这份数据的权威格式说明。底部 `实心体素（重建）` 取消勾选就能看到 journal 原始表面壳。

**这个解码器和 Python 逐位一致，而且有测试守着。** `tools/demo_extract/voxel.py` 算出来的

### 4.3 烟有多深：颜色是量出来的，不是挑出来的

烟雾的深浅**只有一个可调量**：材质的基色 `SMOKE_BASE_COLOR`
（`static/js/visuals.js`）。原因是云心穿过的体素 ~25 个，中心不透明度
`1 − 0.86²⁵ ≈ 0.98`，所以云心画出来的颜色基本就是"基色被灯光打亮"的结果 ——
基色直接决定烟有多深。

**旧值 `0xdfe5ec` 是错的，而且错得很具体**：在 24 团真实烟雾 × 多个视线方向上量，
烟画出来是**背后那块墙的 1.074 倍亮，最坏一团 1.182 倍** —— 烟比它背后的墙还亮。
逐像素差值图更直白：旧值下烟和地图的亮度差大多不到 8/255，轮廓基本看不出来，
看着就是一层发白的雾，而不是一团实心的烟。

**现值 `0xa5a9af`**，是把旧值按 0.74 **等比压暗**：

| | 基色亮度 | 渲染亮度 | 烟/地图 | 最坏一团 | 烟/天空 | 饱和度 |
|---|---|---|---|---|---|---|
| `0xdfe5ec`（旧） | 228 | 167 | 1.074 | **1.182** | 0.869 | 0.045 |
| `0xa5a9af`（现） | 169 | 133 | 0.862 | 0.898 | 0.697 | 0.058 |

"等比压暗"不是随便说说的：手挑的候选（`#c4ccd6` / `#b6bfca` …）绝对蓝偏移越压越大
（+13 → +24），压暗的同时会把烟越配越蓝。按比例缩放色相就不动 —— 上表里饱和度
0.045 → 0.058 基本没变。

（表里的数字是 24 团烟的中位数。单次测试量到的会随"采样到哪几团烟"在 0.82~0.86
之间浮动，所以测试的容差区间留得比这个范围宽。）

**量法**：同一条视线渲染两次，一次藏掉烟、
一次画上，逐像素求差 → 差值大的就是烟覆盖的像素，不用去猜"哪些像素算烟"。
两次渲染在同一个 JS 任务里跑完，所以 `updateSmokeAnimations` 的透明度呼吸插不进来。
背景取的是**被烟盖住的那部分像素**，不是整个画面 —— 比的是"烟 vs 它背后那块墙"。

两个踩过的坑，都写在探针的注释里：

* **相机必须用地图 BVH 挑视线**。一开始按固定方向退开 4 米，相机落在墙里，整团烟
  被挡住，只量到 4 个像素（覆盖率 0.02%），差点得出"烟变淡了"的结论。现在从体素
  质心往外打 64 条射线，挑最空的方向。
* **"芯"不能用"差值大"来判定**。差值大只说明背景和烟的颜色差得多，不说明烟厚。
  所以只看全部烟像素的均值，并且跨多团烟取分布，避免拿单张图定颜色。

**回归测试** `visualizer/tests/test_smoke_color.mjs`（21 项）：

```bash
python visualizer/server.py --port 5099 &
node visualizer/tests/test_smoke_color.mjs http://127.0.0.1:5099 /path/to/match.csz
```

它不只是比对常数，而是**在真实地图上重新量一遍**：逐像素解出烟雾的**有效不透明度
`a`** 和它**自己的颜色 `C`**。做法是同一条视线渲染四次 —— `M`（只地图）、`S`（只天空）、
`Pm`（地图+烟）、`Ps`（天空+烟），于是

```
Pm − Ps = (1−a)(M − S)   →   (1−a) = ⟨Pm−Ps, M−S⟩ / |M−S|²
C = (Pm − (1−a)·M) / a
```

这样 `a` 和 `C` 都跟背后是什么无关。**这四张图必须在线性输出空间渲染**
（`NoToneMapping` + `LinearSRGBColorSpace`）：显示空间里帧缓冲的值已经过色调映射和
sRGB 编码，混色不在线性空间做，上面这个方程根本不成立 —— 我第一版就在显示空间解它，
解出来的 `a` 和 `C` 全是偏的（换颜色只量出 6% 差异，实际是 20%）。

于是测试能同时守住三件事：

* **深度** —— 每一团都比天空暗（天空是稳定又亮的参照，可以要求逐团成立）；烟/地图
  的中位落在 `[0.80, 0.96]`。地图不能要求逐团成立：深色墙角本来就比烟暗，烟比它亮
  是物理上正常的，所以只看中位和"多数"。
* **体积感**（盯的是 `SMOKE_OPACITY`）—— 云心 `a_max` 必须接近 1（不透明），同时
  `0.05 < a < 0.5` 的薄雾过渡带必须占一定比例。否则就不是一团有体积感的烟，而是一块
  硬边贴片。
* **色相** —— 饱和度必须低（中性灰）、`B ≥ R`（偏冷），而且 `(B−R)/亮度` 不能变大
  （这条专门拦"压暗时顺手加深蓝调"）。

最后还有一条**灵敏度对照**：把颜色换回旧值必须量出"明显更亮、而且比墙亮"。
不然这个测试可能只是在自我复读常数 —— 它得真的能测出颜色变化。

## 4.5 小人、下蹲、碰撞盒和眼睛

### 4.5.1 小人长什么样

不是"圆柱 + 球 + 圆锥"了。按真实比例搭，总共 9 个网格：

```
头心 1.64 ── 头盔（半球）/ 面罩（脸前的扁方块，一眼看出朝向）
            └ 头（球，**不随下蹲压扁**）
肩线 1.43 ── 双臂（胶囊）
            └ 躯干（上宽下窄的锥台，肩比腰宽）
胯   0.78 ── 双腿（胶囊）
脚底 0.00
```

总高正好 **72 HU = 站立碰撞盒高度**，脚底在 y=0，所以"头顶 ≈ 碰撞盒顶"，
两个可以叠着看。俯仰改成绕**头心**旋转 —— 以前 `pitchGroup` 挂在脚底，
pitch 90° 时头会荡到身前 1.6 处。

### 4.5.2 小人会跟着蹲下去

身体按**连续**的 `crouch` 压缩 Y，压缩比 `(72 − 18·crouch) / 72`：

| | 站立 | 蹲到底 |
|---|---|---|
| 身体比例 | 1.00 | 0.75 |
| 名义身高 | 72 HU | 54 HU（= 蹲下的碰撞盒高度） |
| 头心离地 | 64.6 HU | 48.4 HU |
| 眼高 | 64.09 HU | 46.09 HU |

头**不跟着压扁**（`head.scale.y` 恒为 1）—— 只压身体。血条和名字跟着头顶走，
否则蹲下时会浮在半空。压缩比和眼睛的下落量共用同一个 **18 HU**。

头顶还挂一块 **选手 ID 牌**（底部 `选手 ID` 开关，默认开）：写的是
`matchData.players[i].name`（取不到名字才退回 `01`–`10` 的槽位号），深色圆角底 +
队色描边、字号比名字大一圈。牌子**高度固定、宽度按文字实测撑开**，太长的 ID
逐级缩字号而不是挤出框外。它和名字是两个 sprite、两个开关，跟着头顶一起下沉。
用 `THREE.Sprite` 是因为 sprite 的朝向由渲染器按摄像机现算 —— 玩家转身、镜头
绕到背后都不用逐帧改旋转，这就是"始终朝向摄像机"
（`visuals.js::createIdTag` / `setPlayerIdNames` / `setPlayerIdsVisible`）。死人的
整组隐藏，ID 牌跟着不画；`renderOrder 980` 在眼睛图标的 990 之下，两个都开时
眼睛仍然完整可见。

> 注意身体跟的是 `crouch`（连续），碰撞盒跟的是 `crouching`（阶跃）。
> 这是**刻意**的：身体是"看起来像"，真实动画本来就是渐变的；碰撞盒是物理真相。
> 两个一起打开就能看到"身体在滑、盒子在跳"。

### 4.5.3 碰撞盒和眼睛

勾上底部 `碰撞盒 / 眼睛` 会画出三样东西，都跟着玩家转（碰撞盒本来就是轴对齐在
玩家局部坐标里的）：

| 画的 | 来源 | 行为 |
|---|---|---|
| 青色 / 橙色线框盒 | `crouching`（`FL_DUCKING`） | **32×32×72 站 / 32×32×54 蹲，阶跃跳变** |
| 绿色小球 | `eye_height` | **64.09 → 46.09 HU，连续滑下去** |
| 绿色竖线 | 同上 | 脚到眼的标尺，用来一眼看出掉了多少 |

**为什么盒子是阶跃的而眼睛是连续的**：这是两个不同的量，不是同一个东西的两种画法。
碰撞盒 `m_vecMaxs.z` 实测**只有 72 和 54 两个取值**，中间没有 55..71；
而 `m_flDuckOffset` 是连续滑到 −18 的。`FL_DUCKING` 甚至不是下蹲量的纯函数
（实测"盒子还是 72 时下蹲量最大到过 0.9998"、"盒子已经是 54 时下蹲量最小到过
0.7516"），它跟的是**下蹲键的意图**。所以：

* 想看"他能不能钻过去 / 打不打得到" → 看盒子（`crouching`）
* 想看"他的相机在哪" → 看眼睛（`crouch`）

把盒子画成渐变的是**错的**，真实的盒子不渐变。两个一起打开，蹲下的那一瞬间就能
直接看到"盒子跳、眼睛滑"。详细的数据论证见 `tools/demo_extract/API.md` §4.12。

瞄准射线（`轨迹` 之外的那条）和**第一/第三人称相机**也是从**真实眼睛**发出的：
以前两处都硬编码 64 HU（`visuals.js` 的 `updateAimRays`、`scene.js` 的 `renderFrame`），
站立时误差可忽略（64 vs 64.0938），蹲下时会差整整 18 HU —— 射线会从站立眼高射出，
第一人称视角会高出半个头。

站立足眼高 **64.0938 HU** 是整条链上唯一一个 demo 说不准的数（CS2 没有网络化任何
视点偏移字段），只能取 Valve 文档值；demo 里唯一的候选 `CCSPlayerPawn.m_vecZ`
众数是 64.000，但它空中读数是垃圾。两者差 0.0938 HU = **2.4 mm**，画面上不可见。
常数在 `static/js/replay-core.js` 的 `STANDING_EYE_HEIGHT` / `CROUCH_EYE_DROP`，
要改改那一处（`visuals.js` / `scene.js` 都从那里 import，没有第二份）。

> ⚠️ 需要 **v7** 的 `.csz`。v6 文件里 `crouch` 列不存在，前端会当成 0（站立）：
> 小人站着、盒子恒为 72、眼睛恒为 64.09。重新提取一次 demo 就有了。

### 4.5.4 走路时腿会摆

小人走路时两条腿前后剪式摆动（反相），摆的**频率跟走过的距离走、幅度跟速度走**。

#### 为什么相位按距离、不按时间

摆腿角是 `θ = A·sin(2π·d / 步幅)`，`d` 是**累积水平位移**，不是时间。

这不是风格选择，是"脚不打滑"的唯一做法：按时间积分的话，步频就得靠一张
"速度 → 频率"的映射表去凑，而且同一个采样点会随**播放历史**摆到不同角度 ——
拖时间轴、倒放、来回拖，姿势全都不一样。按距离积分之后，步频自动等于
`速度 / 步幅`，慢走自然就是慢摆，而且整个步态变成**采样点的纯函数**：

```js
const gait = buildGait(round);   // 每个玩家一份 {phase, amp}，各 n 个采样
```

拖到任意采样点、来回拖、倒着放，姿态都逐位相同（`test_walk_cycle.mjs` 里
专门有一条守着这个）。

#### 参数是怎么定的

| 量 | 值 | 依据 |
|---|---|---|
| `GAIT_STRIDE_HU` | 112 HU / 周期 | CS2 跑速上限实测就是 **250 HU/s**（p90 = 250.0，直方图 225–250 占 40%）。112 HU → 全速 **4.46 步/s**，短跑量级；走速（~130 HU/s）降到 2.3 步/s |
| `GAIT_MAX_SWING` | 0.60 rad ≈ 34° | 全速时的摆角 |
| `GAIT_RUN_SPEED_HU` | 250 | 摆幅的归一化参考；`A = 0.60·min(1, v/250)` |
| `GAIT_CROUCH_STRIDE` | 0.60 | 蹲走步幅更短 → 同样距离摆动次数更多 |
| `GAIT_CROUCH_SWING` | 0.55 | 蹲走摆幅更小 |
| `GAIT_TELEPORT_HU` | 200 | 单采样位移超过这个就是复活 / 回合重置，不推进相位（全速一采样才 3.9 HU） |
| `GAIT_AIR_TAU` | 0.08 s | 起跳 / 落地 / 停步是**阶跃**的，摆幅按这个时间常数平滑，不然腿会瞬间弹回 |

摆幅吃的是 `.csz` 里的 `v` 列（HU/s）。实测 `v` 和逐采样位移算出来的速度**完全一致**
（p50 都是 213.3、p95 都是 250.0），所以两者可以放心互换。

#### 髋部下沉

剪式摆腿的腿是刚体、没有膝盖。髋高不变的话，脚会离地 `L(1−cos θ)`
（全速时 5.3 HU），看着像在飘。所以髋部按 `1 − BOB(1−cos θ)` 下沉（`BOB = 0.5`）：

```
脚离地 = L·(1−BOB)·(1−cos θ)     全速时 2.65 HU（减半）
胯高   = P_LEG_TOP·k·(1 − BOB(1−cos θ))   30.7 → 28.1 HU
前后差 = −2L·sin θ                全速时 ±34 HU
```

（`k = (72 − 18·crouch)/72` 是蹲下的压缩比，`L = P_LEG_TOP·k` 是腿长。）
重心在步幅最大时最低、双腿并拢时最高 —— 和真人走路同相。脚**永远不会低于地面**。

#### 腿为什么不能留在被缩放的那一组里

蹲下原来是把 `bodyGroup.scale.y` 压到 `k`。腿现在要**绕胯旋转**，就不能待在里面了：
父节点非等比缩放 + 子节点旋转 = **剪切**，腿会被压歪、脚会被压扁成椭圆。
（three 的局部矩阵是 `T·R·S`，`S` 最先作用，所以"缩放和旋转在同一个节点"没问题，
"缩放在父节点、旋转在子节点"才有问题。）

所以改成**逐个网格**设 `scale.y`（位置也一起乘），每根腿挂在一个绕胯转的
`legPivot` 上、腿的 `scale.y` 在 pivot **里面**：

```
bodyGroup (不缩放)
├── torso / armL / armR        (scale.y = k, position.y *= k)
├── legPivotL  (position.y = 胯高, rotation.x = +θ)
│   └── legL   (position.y = −P_LEG_HALF·k, scale.y = k)   ← 缩放在旋转内侧
└── legPivotR  (rotation.x = −θ)
```

#### 怎么验的

```bash

```

数据模型那一半（纯 node，直接 import `buildGait`）：相位增量恒为 `2π·d/步幅`、
竖直下落不推进相位、传送不推进、死人 / 空中摆幅归零、摆幅随速度**单调**且在
跑速处饱和、蹲走步幅更短、以及**纯函数性**（算两次逐位相同；只取回合的前缀，
前缀的相位也逐位相同）。

渲染那一半直接量两只脚的**世界坐标**，和上面的解析公式逐项对拍（误差 < 0.05 HU），
再全回合扫一遍确认没有一只脚低于地面、身高恒为 `72 − 18·crouch`（头不受步态影响）、

## 4.6 瞄准射线

勾上工具栏的「瞄准射线」，每个活着的人会从**真实眼睛**沿瞄准方向射出一条线，
在**最近的遮挡**处截断，颜色表示打到了什么：

| 颜色 | 含义 | 长度 |
|---|---|---|
| 🔴 红 `#ff4d4d` | 打到**别的活着的玩家** | 到那个人碰撞盒的**近面** |
| 🟠 琥珀 `#ffb020` | 打到**地图几何**（墙 / 地板 / 天花板） | 到那个三角形 |
| 🔵 暗青 `#66ccff` | 什么都没打到 | 画满 60 m（≈2362 HU） |

命中处会画一个小球当撞击点；红色 / 琥珀色才有，青色没有。
射线和撞击点都是 `depthTest: false`，跟碰撞盒 / 眼睛那层一样，隔着墙也看得见。

起点是**含下蹲的眼高**（`64.0938 - 18 × crouch`），不是硬编码的 64 ——
和 §4.5.3 用的是同一个 `eyeHeightFor()`。方向就是 `yaw` / `pitch`。

### 4.6.1 玩家截断用的是什么

用的是**真实碰撞盒**：`m_vecMins` / `m_vecMaxs`，即世界轴对齐的
`32 × 32 × 72`（站立）或 `32 × 32 × 54`（蹲下）盒子 —— 和 §4.5.3 画的那个是同一个
（高度取 `crouching` 的**阶跃**值，不是连续的 `crouch`）。不随 yaw 旋转，
所以射线-AABB 的 slab 测试就够，不需要 OBB。

> ⚠️ 这是**移动碰撞盒**（`CCSPlayerPawn` 的 hull），是**可射击判定区（hitbox）的超集**。
> 所以"红射线"的含义是"这条视线进入了那个人的碰撞体"，**不等于**"这一枪会掉血"。
> 真正的 hitbox 是骨骼绑定的、会随姿态变形的，demo 里没有。

自己的盒子不算（`j === i` 跳过），**死人不算**（ragdoll 不挡子弹）。

### 4.6.2 地图截断：为什么要写一个 BVH

地图 OBJ 是**单个 mesh、823,214 个三角形**。three.js 的朴素
`Raycaster.intersectObjects(map.children, true)` 实测 **45 ms / 条射线** ——
10 个人一帧就是 450 ms，完全没法用。

均匀网格也不行：三角形大小差 500 倍（中位数 0.44 m，最大的一个 239 m，
是横跨整张地图的地板），1 m 的格子要 **1.38 亿次插入**。

所以 `static/js/map-raycast.js` 自己实现了一个 BVH（约 300 行，**不依赖 three**，
纯 typed array）：

- 按质心范围**最长轴的中点**划分，双指针就地 partition；退化了就按中位数硬切
- 叶子 8 个三角形；遍历时按 slab 进入距离排序，近的先走，远子树直接剪掉
- 顶点表在常见情况下（单 mesh + 单位矩阵 + 非索引几何）**直接复用 OBJ 的
  position 数组**，不多花 30 MB

实测：

| | 朴素 raycast | BVH |
|---|---|---|
| 建索引 | — | **268 ms**（一次，懒建） |
| 单条射线 | 45 ms | **0.0020 ms** |

懒建：不在地图加载时建，而是**第一次打开「瞄准射线」**时建（`ensureMapBVH()`）。
268 ms 是能感觉到的短暂卡顿，所以按钮那一刻会置灰。建好后一直留着，换地图才丢。
建好之前射线只截断到玩家；建好之后数据检查面板会显示
`地图 BVH：823,214 三角形 · 268 ms`。

同一棵树也顺手给 §4.5 里"给尸体找地面高度"那条垂直射线用了
（同一条射线朴素 raycast 也要 45 ms，一回合 10 个尸体就是 450 ms 的一次性卡顿）。

### 4.6.3 正确性是怎么验的

分两层，都能单独跑。

**第一层：BVH vs 暴力扫描**（纯 Node，不需要浏览器，秒级）。除了手搭的解析用例
（单三角形、立方体对角线）之外，主力是**随机三角形汤对拍**：2 万个随机三角形
（1% 是横跨全场的大三角形，模拟真实分布）、4000 条随机射线，BVH 的结果必须和
逐三角形暴力扫描**逐位一致**。遍历剪枝写错几乎必然在这里暴露。

```bash
node visualizer/tests/test_map_raycast.mjs
# map raycast: 34 passed, 0 failed
```

**第二层：BVH vs three.js 自己的 raycaster，在真实地图上**。用真实玩家的眼睛 +
瞄准方向当射线（再补几条朝上朝下的），逐条比对距离。
注意要把地图材质的 `side` 临时改成 `DoubleSide` —— three 默认 `FrontSide` 不命中背面，
而瞄准射线两面都要挡，不改就是不公平对比。

同一支测试还会读**真实场景图里那条 `THREE.Line` 的两个端点**，验证：起点 ==
`(game_x, game_z + eye_height, game_y) × SCALE`、方向 == yaw/pitch、长度 ==
报告的命中距离、红线的终点落在目标碰撞盒**表面上**（往后退 2 cm 必须在盒外）、

## 4.7 子弹曳光

勾上工具栏的「子弹曳光」（**默认开**），每开一枪就从开枪者的**眼睛**沿那一帧的
瞄准方向飞出一小段**曳光弹**（一根 5 m 长的发光圆柱，加法混合）：

* 打到**人**或**障碍物** → 头停在命中点上，闪一下（打人偏红 / 打墙琥珀），
  停 0.06 s 后 0.16 s 淡出；
* 什么都没打到 → 飞满 60 m（和瞄准射线的暗青线同一个上限）再淡出。

```
开火事件（events.sound, ty=fire, 精确 tick + 开枪者）
        │
        ├─ 方向 = 那一帧的 yaw/pitch      ← eyeRay()
        └─ 遮挡 = 最近的玩家碰撞盒 / 地图三角形  ← castRay()
                        ↓
              曳光：fly → hold → fade
```

**开火事件从哪来。** `events.sound` 里 `ty === "fire"` 的那一条，带**精确 tick** 和
开枪者，所以能一发一发地对上。实测它和玩家列的 `shots` 列**逐发相等**
（`test_tracers.mjs` §A 会验证：总数相同、每一发都落在 `shots > 0` 的采样点上）——
两者本来就是同一个 `weapon_fire` 事件的两个投影，用 `sound` 只是因为它有精确 tick。
老 `.csz` 没有 `sound` 字段就回退到 `shots` 列（每个采样窗口内的开枪数）。

**方向 / 遮挡和瞄准射线是同一次检测。** 两者共用 `eyeRay()` 和 `castRay()`，
所以同一帧同一个人，**曳光的终点和瞄准射线的终点必然重合**（测试拿这条当不变量）。
眼睛用含下蹲的眼高，和 §4.6 一样。

**视觉上从"枪口"起。** demo 里的开火方向就是眼睛的朝向，但曳光从眼球中心冒出来
不好看 —— 所以画的时候沿**同一条射线**往前挪 0.35 m（`TRACER_MUZZLE_OFFSET`），
终点不变。

**速度是真实时间的 200 m/s，不随播放倍速变。** 跟倍速的话 4× 时一帧就能跳过整条
曳光。段长固定 5 m，但低帧率下一帧的行程可能超过它（会画成虚线），所以段长会临时
撑到盖住这一帧的行程（上限 2×，免得变成一根几十米的激光）；停住时会收回标称长度。

### 4.7.1 这不是真实弹道

⚠️ demo 里**没有子弹实体**，`fire_bullets`
（`origin + angles + seed + spread` 的理想弹道）**没有提取**。所以这里只有：

| 有 | 没有 |
|---|---|
| 精确的开火 tick、开枪者、武器编号、是否消音 | **spread / 后坐**（方向只有 yaw/pitch） |
| 直线方向上第一个玩家碰撞盒 / 三角形 | **穿透**（打到人不会继续穿） |
| | **距离衰减 / 伤害**（和 `damage` 事件无关） |

也就是说：**曳光停在哪，说明"那条视线被什么挡住了"，不等于"这一枪打中了什么"。**
打人的判定用的还是 §4.6.1 的移动碰撞盒（hitbox 的超集），死人不挡子弹。

## 4.8 可见性眼睛图标（几何驱动）

在左侧玩家卡里**点一下选中一个人**（卡片展开、镜头飞到他旁边并**跟着他走**，
见 §4.11），他**此刻能观测到的其他人**头顶就会出现一个眼睛图标。取消选中
（再点一下那张卡）或关掉 `可见性（眼睛，实时几何）` 开关，图标立刻消失。

> 眼睛图标答的是「**A 看得见谁**」。要看「**我看得见谁**」往下看身体本身：
> `选手 X 光`（默认开，§4.10）会把被墙挡住的选手画成半透明幽灵。

> **这里以前挂的是 `.csz` 的 `spotted` 列（引擎的 `m_bSpottedByMask`），已经撤掉。**
> 现在眼睛图标**只有几何一个来源** —— 逐帧算的 `visibility.js`（详见 §4.9）。
> 撤掉的理由是那两套东西语义不同、时基不同，挂在同一个图标上只会让人分不清
> 自己看到的是哪一个：引擎的 `spotted` 被限速在 **33 tick = 0.516 s 的网格**上
> （下面有实测），而几何是逐帧的；`spotted` 只标敌方，几何走全有序对（含队友）。
>
> 原始 `spotted` 数据**照常提取、照常传输、照常显示在右侧「数据检查」面板**里，
> `__v5.visibleEnemiesOf()` / `__v5.visibleEnemies` 也还在（读数据用），
> 只是不再画成图标。

**渲染**（这一层没变）：图标挂在 `group` 上（不挂 `pitchGroup`），位置每帧按头顶
重算 `(1.64·(72−18·crouch)/72 + 0.19 + 0.72)` 米 —— 和血条 / 名字一样跟着下蹲沉
下去，但**不跟着俯仰角甩**。10 个图标共用一张 canvas 贴图和一个材质（画一次眼睛：
深色圆底 + 眼眶 + 虹膜 + 瞳孔，强调色 `#00e5ff`），`depthTest: false` +
`renderOrder: 990`，所以和名字标签一样不会被墙挡住 —— 这个功能看的是**判定结果**，
不是"相机能不能看见"，被墙挡住反而没法对照。

### 4.8.1 引擎 `spotted` 列的两个坑（数据还在用，所以还记着）

**方向是反的。** `spotted[E]` 记的是「**能看到 E 的敌人**」，不是「E 能看到的
敌人」（见 `tools/demo_extract/API.md` §1.6）。搞反了照样有图标，只是全标在错的
人头上，而且不会报任何错。所以这里有两道独立的防线：

1. `replay-core.visibleEnemiesOf()` 里只写一处反向查找，注释里写明；
2. `test_spotted_payload.py` 拿**几何**独立验证：把 `spotted[i]` 里单向出现
   （`i ∉ spotted[j]`）的 (i, j) 对挑出来，量两个人的朝向和连线的夹角 ——
   实测 471 对里 **j 有 94.9% 在看着 i**，而 i 只有 52.2%。所以确实是 j 在看 i。

**死人必须自己滤掉。** `approximate_spotted_by` 在 pawn 消失（死亡）之后
**留着最后一个值不清零**：实测 de_inferno 一整场 130,519 个 spotted 对里，
123,310 个的"看到者"其实已经死了，另有 1,174 个的"被看到者"已经死了。
不滤的话会看到"死人的眼睛飘在活人头上"。所以 `visibleEnemiesOf()` 要求
**看的人和被看的人都活着**，测试里专门扫一整个回合守这条不变量。
（几何判定本身两侧都要求 `alive`，不需要这道补丁。）

> ⚠️ **`spotted` 被限速在 33 tick = 0.516 s 的网格上。** 实测（de_inferno 24 回合）：
> mask 的每一次变化都落在 `tick % 33` 的**同一个余数**上（24/24 回合、105/105 段
> 连续存活区间都只有一个余数；ON 的驻留长度只有 33/66/99/132 这几种），而同一批
> 采样点上的 `x/y/z/yaw/pitch/ducking/shots_fired/inventory` 全都**没有**这种量化
> （33/33 个余数都有，x≈1.0）—— 所以这不是 demo 传输的假象，是引擎的游戏系统
> `CCSEntitySpotting` 自己按 33 tick 更新。**没有任何 cvar 能关掉它。**
> 直接后果：从「真的能看见」到「`spotted` 变 1」**平均慢约 178 ms**（640 个伤害
> 事件里，mask 在 32 tick 内翻成 1 的那 85 个，延迟均值 11.39 tick）。
> §4.9.5 用几何独立量了一遍：均值 14.4 tick = 224 ms，范围 1~31 tick。
> 另外 `m_bSpotted` **还会被声音置位**（枪声 / 脚步），几何判定不含这一项。

`spotted` 和 `approximate_spotted_by` 实测**完全冗余**：2,172,400 行原始数据里
`spotted == (mask != 0)` 的不一致率 **0.0000%**，所以 `.csz` 里只存了后者推出来的
那一列，bool 没存。数据是 `--no-spotted` 提取的老文件里没有这一列 →
右侧「数据检查」面板的 `spotted 可见性` 那行会直接写「无」（**但眼睛图标不受影响**，
它现在不依赖这一列了）。传输上和 `inventory` 一样走**稀疏**（只在变化时记
`{i, v}`）：实测一整场 24 回合的 `spotted` 只有 740 个变化点，一个回合 39 个。

## 4.9 几何可观测性（实时算「B 能不能看到 A」）

这一节就是 §4.8 那个**眼睛图标的判定来源**：纯几何、逐帧、自己算。

> **这里以前有第二个来源** —— `.csz` 里的 `spotted` 列（引擎的
> `m_bSpottedByMask`，带一个实测 **33 tick = 0.516 s 的限速网格**，同一回合 10 个人
> 共用一个相位；见 §4.8.1）。现在**撤掉了**：两套东西语义不同（含不含队友）、时基
> 不同（逐帧 vs 33 tick 网格），挂在同一个图标上只会让人分不清看到的是哪一个。
> `spotted` 数据本身照常提取、传输、显示在数据面板里。

### 4.9.1 判定规则

对每一个**有序对** `(B, A)`（10×10，只排除自己，**包含队友**）：

```
眼睛(B) → A 的碰撞盒 8 个角落
对每个角落：
  ① 方向在 B 的视锥里吗？        水平 90° × 垂直 58.7°（16:9），矩形视锥不是圆锥
  ② 眼睛到角落之间撞地图了吗？   已有的 823k 三角形 BVH
  ③ 撞烟雾体素了吗？             已有的 32³ × 12 HU 实心体素栅格，Amanatides–Woo 3D DDA
  三个都过 → 这个角落「通」
8 个角落里**任意一个通** → A 能被 B 观测到
```

三个选择是**刻意的**，都有代价：

| 选择 | 代价 |
|---|---|
| 8 个角落任意一个通就算可见 | 比「打中心一条射线」宽松：墙后只露出半个头也算可见 |
| 包含队友 | 和 `spotted`（只标敌方）语义不同，眼睛图标会多出队友（**故意的**） |
| 只看几何 | 没有声音 / 被闪 / 开火暴露 / 距离衰减 |
| 逐帧、无延迟 | 和引擎那 33 tick 的网格对不上，两个数放一起比会打架（见 §4.9.5） |

碰撞盒是 `32×32×72`（站立）/ `32×32×54`（蹲下），世界轴对齐，不随 yaw 转 ——
和 §4.5.3 画出来的是同一个盒子。判定盒往内收 **1 HU**：不收的话脚部那 4 个角落
正好落在地板平面上，命中距离和 `maxDist` 在浮点上分不开，而 BVH 用的是严格
`hit < maxDist` —— 误差符号随机，同一个姿势会**时通时不通**（帧间闪烁）。

### 4.9.2 为什么能实时

`visualizer/static/js/visibility.js` 是**纯模块**（不 import three），地图遮挡通过
注入的 `castMapRay` 回调进来 —— 于是它能在 node 里直接跑对拍测试，也对坐标系无感。
实际接线走 `makeMapCaster(bvh, SCALE)`：`game → three` 是 `(gx,gy,gz) → (gy,gz,gx)·S`，
**方向向量只做同样的轴置换、不乘 SCALE**（这个置换是循环移位，是个旋转，长度不变）。

省时间的三个地方：

* **视锥早退** —— 视锥外的角落**根本不发射线**。实测 90 对里只有 52 条射线要发。
* **第一个通的角落就收工** —— 已经确定可见，剩下 7 个角落不测。
  （`exactCount: true` 可以关掉它换到精确的「通了几个角落」，判定结果不变。）
* **烟雾先做 AABB 拒绝** —— 384 HU 的立方，绝大多数射线 3 次 slab 就被排除，
  根本进不了 DDA。

| 场景 | 每帧 |
|---|---|
| 82 万三角形合成地图，90 对（默认路径） | **0.100 ms** |
| 同上，`exactCount`（8 个角落全测） | **0.117 ms** |
| 上界：720 条射线 × (BVH + 2 个烟的 DDA) | **0.583 ms** |
| 真实 de_inferno（headless Chrome，热态中位） | **0.50 ms**（52 条射线/帧） |
| 视锥（8 段线，不需要射线） | 可以忽略 |

BVH 建一次 145 ms（82 万三角形），懒建、按对象身份缓存，换地图才重建。

眼睛图标**默认开着**，所以这份矩阵是**每帧**算的（三个开关全关掉时一次都不算，
开销为 0）。BVH 没就绪时几何只按视锥 + 烟雾判（不算墙），建好后
`ensureVisEvaluator()` 按 BVH 的**对象身份**检测到变化会自动重建求值器 ——
只判 `null` 的话换地图后会继续拿旧 BVH。

### 4.9.3 怎么用

页脚三个开关：

* **可见性（眼睛，实时几何）** —— 默认开着。眼睛图标就是这份几何判定的结果
  （§4.8），**没有别的来源**。打开时会先建地图 BVH（一两秒，会显示 busy）。
  **需要先在左侧卡片选中一个人。**
* **视锥** —— 把选中玩家的视锥画出来：从眼睛沿瞄准方向的四棱锥，4 条棱 + 远端
  4 条边（8 段），远端截面在 **25 m** 处，半宽/半高用的就是判定那组半角
  （水平 90° / 垂直 58.7°，16:9）—— 所以画出来的**就是判定用的那个锥**，不是
  另画一个"示意"。只画选中的那一个（10 个叠一起没法看）。**不需要 BVH**，所以是
  同步的、立刻生效。需要先选一个人。
* **可见性角落射线** —— 把选中的观察者到每个目标 8 个角落的 72 条射线**全画出来**，
  颜色就是判定结果：绿=通、红=被地图挡、橙=被烟雾体素挡、灰=不在视锥里
  （根本没发射线）、紫=被别的玩家挡。用来肉眼验证几何到底在算什么。

视锥和角落射线都是 `depthTest: false` 的调试层（和瞄准射线、眼睛图标一样），
所以不会被墙挡住 —— 看的就是判定结果，被挡反而没法对照。

控制台钩子：

```js
__v5.visibility.matrix()        // 10×10 矩阵，matrix[b][a] = 「b 看得见 a」，对角线 null
__v5.visibility.visibleOf(3)    // 3 号能观测到的全部其他人（含队友，升序）
__v5.visibility.stats           // { pairs, rays, mapHits, smokeHits, ms, occluders, mapReady }
__v5.visibility.pairsOf(3)      // 每个角落的明细 {x,y,z,clear,reason,distance}
__v5.visibility.cornerRays()    // 角落调试层画了几段
__v5.visibility.frustum()       // 视锥：远端 4 个角的世界坐标（米）/ 张角 / 起点
__v5.visibility.iconsEnabled    // 眼睛图标开关（= toggle-spotted）
__v5.visibility.frustumEnabled  // 视锥开关（= toggle-frustum）
```

Node 里直接当模块用（不需要浏览器）：

```js
import { createVisibilityEvaluator, makeMapCaster } from './visibility.js';
const ev = createVisibilityEvaluator({ castMapRay: makeMapCaster(bvh, 0.0254) });
ev.setOccluders(smokeOccludersAt(round.smoke, tick));
const m = ev.evaluate(playerStates);
m.visible[b * m.n + a];    // ⚠ 方向是「b 看得见 a」，和 spotted[a] ∋ b 相反
```

### 4.9.5 和引擎 `spotted` 差多少（实测）

de_inferno，aurora-vs-vitality m2，152 个采样点、5782 个敌对有序对：

```
引擎说看得见  11 对 → 几何同 tick 确认 8      （72.7%）
几何说看得见  35 对 → 引擎同 tick 只有 8      （22.9%）
                      往后 33 tick 内又跟上 11（31.4%）
引擎跟上的延迟：均值 14.4 tick = 224 ms，范围 1~31 tick（理论上界 33）
队友对里几何判可见 361 个（引擎一个都没有，符合预期）
```

**「同 tick 只有 22.9%」不是几何算错了，正是这个工具存在的理由** —— 引擎的
`spotted` 最快也要 33 tick 才更新一次，同 tick 比是系统性偏袒几何的比法。放宽到
33 tick 的窗口后引擎跟上了一部分，延迟落在 1~31 tick 内，和 §4.8 量到的
**33 tick 网格**完全吻合。

两个方向的分歧各有解释，都不是 bug：

* **引擎看得见、几何看不见**（3 对）：视锥 1 对、地图 2 对；其中 **2 对（67%）**
  的目标在之前 33 tick 内**开过枪或走过路**。引擎的 `m_bSpotted` **会被声音置位**，
  本工具是纯视觉的。样本只有 3 对，只能说"和声音假说一致"，不能当结论。
* **几何看得见、引擎一直没跟上**（11 对，其中 5 对是窗口内有人死了判不了）：
  「任意一个角落通」本来就比引擎宽松（半个头露出掩体也算），而且引擎可能用
  单条射线打中心。

### 4.9.6 已知限制

* **FOV 是常量 90°（水平），这个数是挑的，不是提取的。** 实测（de_inferno
  aurora-vs-vitality m2，2,172,400 行）它「对一半」：
  * 引擎自己的默认值**就是 90** —— `m_iFOV` 只有 `0`（=用默认，95.23% 的活人
    tick）、`90`（2.36%）、`40`（2.04%）、`10`（0.37%）、`15`（~0）这 5 个值。
    所以**不开镜时是对的**。
  * `40 / 10 / 15` 是**开镜档位**，坐实的不是猜的：`40` 有 97.8% 出现在持 AWP 时
    （其余 2.2% 是 SSG 08），`10` 100% 是 AWP，`15` 100% 是 SSG 08。
    **持 AWP 时有 64.7% 的 tick 在 40 或 10** —— 也就是一个架枪的狙击手视野是
    40° 或 10°，这里按 90° 算，**恰好错在可见性工具最该看对的场景上。**
  * 真字段是 `CCSPlayerPawn.CCSPlayer_CameraServices.m_iFOV`（`0` = 用默认 90）。
    ⚠️ **不是** `CCSPlayerController.m_iDesiredFOV` —— 那个在 demo 里 153 万行
    **全是 0**，是死字段。这个字段死人身上不留陈旧值（死人 100% 是 0）。
    提取成本几乎为零：全场 10 人一共只有 **394 次变化**（每 tick 存是 2,172,400
    条），和 `spotted` 的 740 次同量级。
  * **当前决定：不提取，就用这个常量。** 要接真值的话
    `createVisibilityEvaluator({ fovDeg, vFovDeg, aspect })` 已经能覆盖，
    `extract.py` 加一列即可。
  * ⚠️ **另有一个没验证的点**：`m_iFOV=90` 是「16:9 下的水平角」还是 Source
    传统的「4:3 基准水平角」（宽屏 Hor+ 加宽）？若是后者，16:9 下真实水平角
    ≈**106.26°**、垂直角 ≈73.74°，那 90°/58.7° **两个方向都窄了**。
    没能验证（Valve wiki 连不上、搜索拿不到）—— **标为未验证，不猜。**
* **没有声音 / 被闪 / 开火暴露 / 距离衰减**。纯视觉。所以和引擎的 `spotted` 比，
  会有一小部分"引擎看得见、几何看不见"的对，实测那 3 对里 2 对的目标在之前
  33 tick 内开过枪或走过路（§4.9.5）。
* **包含队友**，和 `spotted` 的「只标敌方」不是一个语义。这是**故意的**。
* **其他玩家的身体默认不算遮挡**（`blockPlayers: false`）。打开是一行的事，
  但成本会上去（每个角落多 8 次射线-AABB）。
* **不模拟 peekers' advantage / 网络延迟 / 引擎的时序**，只看这一帧的几何。
* 烟雾用的是**重建出的实心体素云**（和 §4.2 渲染的是同一份），不是游戏里的
  sprite 体积 —— sprite 只影响画面，不影响这里的遮挡。
* **视锥的 25 m 只是画多长**，不是判定距离 —— 判定不看距离，隔半张图只要没遮挡
  也算看得见。25 m 是挑出来的：再长会盖满整张图，再短看不出张角。

## 4.10 选手 X 光（被墙挡住的选手也画出来）

**默认开着。** 被墙挡住的选手不再是"画面上根本不存在"，而是画成一层半透明的
幽灵；**直接看得见的照旧是不透明的正常外观**。于是"真的看到"和"透过墙看到"
一眼能分开 —— 这两种在回放里是完全不同的信息，混成一种就都看不出来了。

> 为什么要有这个：这类回放里最要看的东西恰恰是"这一枪隔着什么打的""他到底在
> 墙后还是墙角外"。以前站在墙后的选手**整具身体都不画**，只剩一个
> `depthTest: false` 的名字标签飘在墙上（§4.8 的眼睛图标、血条、武器图标
> 都是不测深度的），于是既看不出他在哪，也看不出他是不是真的露在外面。

| | `透视地图` | `选手 X 光` |
|---|---|---|
| 改什么 | **地图**换成 15% 不透明的灰色基本材质 | 地图一动不动 |
| 小人 | 全部变成"不测深度 + 自发光"（一个样） | 只有**被挡住的那几个**变半透明幽灵 |
| 直接可见 / 隔墙可见 | **分不出来** | 一眼分得出来 |
| 默认 | 关 | **开** |

两个开关都会写小人身上的材质，所以规则只有一条：**贴材质的动作只有一处**
（`visuals.js::applyFigureMaterials()`，由 `updatePlayers()` 每帧调）。透视地图
开着时幽灵让位（那已经是另一套外观了），`setXRayMode()` 在遍历前把幽灵收回、
遍历后再按判定贴回来 —— 不这么做的话，那趟遍历会把"当前材质"记成幽灵材质
（`_origMat`），关掉透视地图之后就再也还原不回正常外观了。

### 4.10.1 判定：从**摄像机**量，不是从选手的眼睛量

`player-xray.js`（纯几何，不 import three，node 里直接可测）。

和 §4.9 的几何可观测性同源但**方向不同**：那边是「选手 B 看不看得见选手 A」，
有视锥、逐 8 个角落；这边是「**这台摄像机**看不看得见某个选手」，**没有视锥**
（屏幕上看得见就是看得见），只问摄像机到身上那几个采样点之间有没有东西。

判「被挡住」需要三件事里**一个都没通**（任何一个采样点通 = 直接看得见）：

1. 摄像机到采样点之间没有**地图三角形**（走 §4.6.2 那个 BVH）
2. 摄像机到采样点之间没有**烟雾体素**（和 §4.9 共用 `smokeRayBlocked` 的 DDA）

射线在**采样点上就停**（`maxDist = 距离 − 1 HU`），所以选手背后的墙不算遮挡 ——
不然一个贴着墙站的人会被判成"隔墙可见"。1 HU 的容差和 §4.9 的 `HULL_INSET_HU`
同一个理由：腿那个采样点离地只有 ~11 HU，站在斜坡或箱子上时命中距离和射线长度
在浮点上分不开。

### 4.10.2 采样点是**身上三个点**，不是碰撞盒的 8 个角落

碰撞盒是 32×32（半宽 16 HU = 0.41 m）的方盒，比画出来的那具身体（肩宽约 10 HU）
**宽得多**，它的 8 个角落在身体外面的空气里。用一个只从掩体后露出半个肩膀的
选手试一下就知道了：按角落判会判成"看得见"（角落里有一根射线通了），可他其实
只露出一点点；反过来贴着墙站的时候角落又容易穿进墙里，判成"看不见"而其实露着头。

所以这里沿身体中轴取**头（0.88）/ 胸（0.5）/ 腿（0.16）**三个点（0 = 脚底，
1 = 头顶），**任何一个通就算直接看得见** —— 和屏幕上那具身体对得上。0.88 就是
站立眼高（64/72），0.16 是故意不取 0：正好落在地板平面上会和地面三角形打架。

三个点的高度按**画出来的**身高算（`drawnHeightFor`）：`72 − 18·crouch`，跟着
**连续**的 crouch 压下去（§4.5.2 那具身体），**不是**碰撞盒那个 72/54 的阶跃。
实测差别就是"一堵 58 HU 高的矮墙"：站着的人头顶露在外面（直接看得见），同一个
人蹲下（头顶 54）就整具身体都在墙后（幽灵）。

### 4.10.3 幽灵长什么样

正常材质的**克隆** + 四个改动：`opacity 0.42`、`depthTest = false`（这就是
"透视"的字面意思）、`depthWrite = false`、自发光 = 本体色（不然幽灵是阴影里的
黑块）。绘制顺序 `renderOrder = 980`，排在所有不透明物之后。

**颜色 / 自发光是每次贴幽灵时从源材质现取的**（`applyFigureMaterials()`），
不是克隆那一刻的快照。原因是**队色根本不在材质里，只在每回合的 `teams[]` 里**：
`createPlayers()` 建人的时候一个回合都还没加载，只能按 `i < 5` 猜一个底色，而
`.csz` 里的分队是 `['T','CT','T','CT',…]` 这种交错（§4.10.5 那个 bug）。源材质
（躯干 / 双臂 / 头盔共用的 `teamMat`）每帧都被 `updatePlayers()` 灌进真实队色，
幽灵跟着它走就一定对。

**必须克隆**：腿 / 头 / 面罩 / 视线锥用的是 10 个人**共享**的材质（§4.5.1），
就地改会把 10 个人一起变成幽灵。克隆出来的那一份只属于一个人的一个部件。

名字 / 血条 / 武器图标本来就是不测深度的 sprite，所以幽灵身上这几样照旧正常
显示 —— 队色和武器也就还在，不用靠幽灵的颜色去分辨敌我。

### 4.10.4 性能与退化

10 个活人 × 3 个采样点 = **30 条射线上限**，而且"第一个通的采样点就收工"。
`test_player_xray.mjs` 里 13 万三角形的"类地图"上实测 **0.02~0.03 ms/帧**
（和只发 30 条长射线的纯成本同量级）；真实地图（de_inferno，82 万三角形，
headless + swiftshader）冷启动那一帧 **0.20 ms**。两者都在噪声级。

* **BVH 没建好时谁都不会被判成幽灵** —— 那会儿地图还没加载，也就没有墙。这不是
  兜底，是正确结果（`mapReady: false` 会出现在 `__v5.playerXray.stats` 里）。
  BVH 是懒建的，`main.js` 在 `loadMap()` 之后无条件建（§4.6.2）。
* 死人 / 空位**不参与**（本来就不画），省下的射线是实打实的。

### 4.10.5 正确性是怎么验的

`node visualizer/tests/test_player_xray.mjs`（**纯 Node**，不需要浏览器、demo、
地图文件；已挂在 `run_all.ps1` 里）：

* **A 解析用例** 能手算出答案的几何：空地 / 一堵全高墙 / 一堵只到 z=50 的矮墙
  （头顶露出来 = 直接看得见）/ 同一个人蹲下（头顶 54 = 幽灵）/ 墙在选手**后面**
  不算遮挡 / 摄像机正好落在采样点上（距离退化时**一条射线都不发**，不会算出 0/0）。
* **B 暴力对拍** 随机三角形汤上，判定必须和**逐三角形暴力扫描**逐条一致。跑两遍：
  先对纯逻辑（暴力 caster），再对**整条真实链路**（`buildBVH` + `makeMapCaster`
  的轴置换和 SCALE）—— 后者是真正会在浏览器里跑的那条路。两遍都断言样本里
  "看得见"和"被挡住"**都出现过**，否则对拍是空转。
* **C 语义** 烟挡 = 幽灵、`smoke: false` = 直接看得见、烟在选手后面不算、墙先命中
  时不再去问烟。
* **D 不变量** 死人 / 空位 / 空输入 / `states` 为 `undefined`、结果数组复用
  （不每帧分配）、人数变多自动长大、统计自洽（只数活人、`rays ≤ 活人 × 3`）。
* **E 性能** 13 万三角形类地图上 10 个选手的每帧耗时 + 30 条射线的纯成本对照。

浏览器侧的接线在 `visualizer/tests/test_player_xray_render.mjs`（node + Chrome，
43 项）：开关默认开 / `__v5.playerXray` 在 / **用 `__v5.rawRaycast` 自己把 3 条采样
射线重算一遍**（12 个采样点 × 10 人逐条对齐，故意不复用 `player-xray.js`）/
逐个部件读**真实材质**（0.42、不测深度、`renderOrder 980`、9 个部件全换）/
共享材质没被改坏 / 颜色和自发光跟得上 `teams[]` / 和透视地图来回切 / 关掉开关再打开。

它抓到过三个**没有报错的**真退步，都留在代码注释里了：

* **幽灵的躯干会悄悄变成实心。** 材质是"活在网格上"的，`updatePlayers()` 里那句
  `pg.body.material.opacity = 1` 写的是**当前**材质 —— 也就是上一帧留在躯干上的
  幽灵材质。于是只要某个选手在某一帧从"被挡住"变成"看得见"，他的躯干幽灵就被
  永久改成不透明。修法是**先贴材质、再改属性**，并且每次贴上幽灵都把它的四个
  属性重置一遍（`applyFigureMaterials()`）。
* **开着透视地图时小人不再画在地图之上。** 同一个函数还写 `renderOrder`，每帧把
  透视地图那趟遍历设的 999 冲成 0。修法是 `!xrayEnabled` 时才碰材质 —— 透视地图
  开着时材质和绘制顺序**整个**归 `setXRayMode()` 管。
* **幽灵的整体颜色是反的**（§F）。幽灵的自发光是 0.5 强度的本色，占了幽灵画面的
  一大半，而这份本色是**克隆那一刻**的快照 —— `createPlayers()` 建人时一个回合还
  没加载，只能按 `i < 5` 猜"前五个是 CT"，可 `.csz` 的分队是
  `['T','CT','T','CT',…]` 这种交错。于是猜错队的那些幽灵整体发错色的光：**蓝色
  CT 的幽灵发黄、黄色 T 的幽灵发蓝**，看起来就像两队颜色被对调了。非幽灵状态看
  不出来（队色每帧写在"当前材质"上，也就是幽灵那份克隆上，本体反而一直是猜的
  底色），所以只有 `选手 X 光` 会露馅。修法是**颜色不从快照来**：队色写在队服材质
  本体上，幽灵每次贴上时从它的源材质 `copy()` 颜色和自发光（`applyFigureMaterials()`），
  `__v5.playerXray.ghosts` 也顺带把每个部件画出来的 `colors` / `emissives` 报出来。

`test_crouch_render.mjs` 里那段测**透视地图**的断言现在会先把 `选手 X 光` 关掉再
测、测完恢复 —— 幽灵**也是** `depthTest: false`，不隔离的话分不清深度是谁改的。

### 4.10.6 已知限制

* **判定是二值的**，没有"露了一半"的中间态：三个采样点里有一个通就是直接可见
  （整具身体照旧不透明），三个都堵就是幽灵。半身掩体按"露没露出采样点"分。
* **不看视锥**：选手在摄像机背后、屏幕上根本不在视野里，只要中间没东西也算
  "直接看得见"。判定的是**有没有遮挡**，不是"这一帧屏幕上有没有他"。
* **第一人称下它等于"选中玩家看得见谁"** —— 摄像机就在那个人的眼睛上。但那和
  §4.8 的眼睛图标不是一回事：那边走的是"视锥 + 8 个角落"，这边是"摄像机的
  采样点连线"。
* **烟雾算遮挡**（和 §4.9 一致：烟里看不见人）。烟一多，整片区域的人都会变成
  幽灵，这是判定结果而不是画错了。要关掉就是 `createPlayerXRayTester({ smoke:
  false })` 一行。
* **幽灵不参与开火闪光**（`state.flash`）。闪光是往材质上写自发光，而幽灵的自发光
  就是它"整体一个色"的来源 —— 两者会互相覆盖。挡住的人本来也看不清开火，曳光
  和枪口火焰照旧照常画。
* **手里的真实武器模型不在幽灵范围内**（`选手 X 光` 只换身体的 9 个部件）。它是
  异步挂上来的、挂在 `group` 而不是身体组上。后果是良性的：那把枪用的是正常材质
  （照旧测深度），所以它仍然被墙挡住，画面上不会出现"浮着一把实心枪"，只是幽灵
  身上看不见枪。名字 / 血条 / 武器图标是 sprite，照旧显示。
* 视角切换 / 拖拽镜头时判定**每帧重算**，所以镜头一动，幽灵的归属会立刻跟着变，
  没有平滑过渡。这是刻意的：平滑会让"他到底在墙后吗"变得含糊。

## 4.11 相机跟随（选中一个玩家之后镜头跟着他走）

在左侧卡片点一下选中一个人（或在 3D 里直接点小人），镜头平滑飞到他旁边 **8 m 外、
高 5 m**，然后**继续跟着他走** —— 他跑，镜头跟着跑，他始终在画面里。

### 4.11.1 怎么跟的：搬位移，不是每帧重新对焦

每一帧算出玩家这一帧的**世界坐标位移** `delta`，把 `camera.position` 和
`controls.target` **同时**加上它。三个直接结果：

| | 为什么 |
|---|---|
| 相对视角**完全不变** | 平移不改变"从哪个角度看、离多远"，所以跟着的时候照样能拖鼠标绕着他转、滚轮拉近拉远 —— 每次拖拽只是换了这个固定的偏移量，两者不打架 |
| **不用平滑 / 弹簧** | 位置本来就在采样点之间线性插值（`replay-core.js` 的 `getPlayerState`），位移逐帧连续，跟着走既不滞后也不抖 |
| 复活 / 换回合**不会把人跑丢** | 瞬移时 delta 很大，但镜头跟着搬，偏移量不变 |

位置在 `scene.js` 的 `renderFrame` 里跟着搬（只有 orbit 模式；first / third 有自己的
跟法）。

**飞过去的那 0.7 s 也要跟**：跟随把飞行轨迹的 `from/to` 两端一起平移
（`lerp(a+d, b+d, k) === lerp(a,b,k) + d`，缓动本身不变），所以到站时镜头正好停在
玩家**此刻**的位置，而不是点击那一刻的快照。

> **基准点必须显式灌进去。** 跟随是拿位移累加的，基准点（"上一帧他在哪"）如果从
> 下一帧现取，这一帧的位移就丢了 —— 镜头会**永远**差这一个帧的量。实测 dt = 1/30 s、
> 250 HU/s 时是 **0.21 m**，而且一直留着。`setFollowPlayer(idx, worldPos)` 的第二个
> 参数就是干这个的：`focusCameraOnPlayer()` 把这次飞行的目的地（= 点击那一刻他的
> 坐标）当基准点传进去。这条是 `test_camera_follow.mjs` 抓出来的。

### 4.11.2 什么时候停

跟随的语义是「跟着**选中的**那个人」，所以选中状态一变它就跟着变：

| 动作 | 结果 |
|---|---|
| 再点一次那张卡片 | 取消选中 → 停止跟随 |
| `📷 重置视角`（或按 `R`） | 停止跟随（视角回到整张地图/自由视角） |
| 切到 `1st / 3rd Person` | 停止跟随（那两种模式自己跟着 `focusedPlayerIdx`；留着的话基准点会一直不更新，切回 orbit 的第一帧就是一次横跨地图的瞬移） |
| 换回合 | **接着跟**：卡片重建之后自动接回来，并且重新飞一次他新回合的出生点（人换回合是瞬移，只靠位移累加会让镜头硬生生瞬移过去；重新飞是 0.7 s 的平滑过渡，落点也更准） |
| 按 `W/A/S/D`（`Q/E`）推机位 | **取消选中 + 停止跟随**（见 §4.12）—— 手动推机位和"跟着某个人"同时成立会互相拽 |
| 底部 `跟随选中玩家` 开关（默认**开**） | 关掉 = 立刻停止当前跟随，并且之后选中玩家**只飞过去、不跟** |

选中的时候会弹一句提示（`🎥 镜头跟随 <名字>`），不然"镜头为什么自己动"没有解释。

### 4.11.3 怎么验的

```bash
python visualizer/server.py --port 5099 &     # 需要一个在跑的 visualizer
node visualizer/tests/test_camera_follow.mjs http://127.0.0.1:5099 \
     app/data/csz/aurora-vs-vitality-m2-inferno__ca728317.csz
# camera follow: all checks passed（50 项）
```

量的是**场景图里的相机**（CDP + headless Chrome），不是数据：

* 点卡片 → 跟随目标是那个人、卡片展开、飞行动画在跑、提示弹出来了；
* 走完飞行 → 落点**正对着此刻的人**（误差 < 1 cm）；
* 继续播放 → 镜头的位移**逐分量等于**玩家的位移（< 5 mm）、视角中心跟着搬、
  摄像机到视角中心的偏移不变、他仍然在正中心；
* 再点一次卡片 / 重置视角 / 关掉开关 → 跟随立刻停，而且**人继续跑、镜头一动不动**；
* 开关关掉时仍然会飞过去（只是不跟）；
* 换回合 → 跟随接回来、重飞的落点又在他身上；
* WASD（见 §4.12）→ 镜头按 **W 沿水平视线前进 / D-A 屏幕左右 / E-Q 升降**、
  朝向和距离一点不变、松开立刻停，而且**选中被取消、跟随被停掉**；
  焦点在 `<select>` 里按 WASD（下拉框会"打字跳选项"）**不该动镜头，也不该取消选中**；
* 控制台没有报错。

推帧用的是新增的 `__v5.stepFrame(dt, draw)`（一个 JS 任务里连着推固定 dt）：headless
的 rAF 只有 1~3 fps，而主循环里 `if (dt > 0.25) dt = 0.25` 会把掉帧削平 —— 按墙钟
量出来的是帧率，不是跟随。`draw: false` 是这一帧不碰 GPU（相机的位移计算和绘不绘制
无关），不然一次 65 MB 地图的绘制要几百毫秒。

## 4.12 WASD 手动推机位

`W/S` 沿**水平**视线方向前后、`A/D` 屏幕左右、`Q/E` 升降，`Shift` 加速
（15 → 40 m/s）。按住就动，松开就停。

**只搬机位，视角一点不动**：位移同时加到 `camera.position` 和 `controls.target`
上（和右键平移、和相机跟随是同一个"整体平移"动作）。只搬相机不搬 target 的话，
镜头会变成绕着 target 甩 —— 那和"移动机位"不是一回事。W/S 走的是视线的**水平**
投影，所以低头推 W 不会钻到地下。

**按 WASD 会自动取消选中玩家**（卡片收起 + 停止相机跟随，`deselectPlayer()`）。
"我在推机位"和"镜头跟着某个人"同时成立的话，两边会抢同一个 `controls.target`。

接线方式是 `scene.js` 的 `setManualMoveHandler()` 回调，而不是在 main.js 里再听一次
`keydown` —— 谁来听键盘不重要，重要的是**镜头真的被推动了**：

* 焦点在下拉框里时（回合 / 倍速 / 批次选择器）**不记移动键**：Chrome 的下拉框本身
  就是"打字跳选项"，不拦的话按 W 会一边换回合一边把镜头推走。这时回调不会被调用，
  选中状态也就自然保留（`test_camera_follow.mjs` 正面测了这条）；
* 飞行途中的话，按 WASD 会**掐掉飞行动画**（手动输入优先于动画）；
* `fly` 模式（仅控制台可达）用的是同一套键，也同样会退出跟随。

```bash
node visualizer/tests/test_camera_follow.mjs http://127.0.0.1:5099 /path/to/match.csz
# 其中 "WASD pans the camera" 一段：15 项
```

## 4.13 第一人称摄像机

左侧玩家卡片点开之后，详情最上面有一条 **🎥 摄像机** 下拉：

| 选项 | 行为 |
|---|---|
| 跟随镜头（默认） | 原来的 orbit 行为：飞到选手旁边，跟着他走，可拖拽 / 滚轮 / WASD |
| 👁 第一人称摄像机 | 镜头锁在该选手眼睛上，屏幕中心画准星，下方显示实时 HUD |

### 4.13.1 镜头为什么是"锁死"的

进入时 `scene.js` 的 `cameraMode` 切到 `first`，每帧用该选手的
`x/y/z + eye_height` 和 `yaw/pitch` 摆相机：

* `setCameraMode('first')` 把 `controls.enabled` 置为 `false`，鼠标拖拽 / 滚轮 /
  右键平移全部失效；
* `renderFrame()` 的 `first` 分支只读选手状态，**不读** `keys`，所以 WASD/QE
  也推不动镜头；
* 3D 视口点击选人、卡片点击换人、`跟随选中玩家` 开关都不会影响这个镜头；
* 进入时保存 `camera.position` 和 `controls.target`，退出（Esc / HUD 退出按钮 /
  重置视角 / 换回合）时原样恢复，所以出来之后还是进入前那个 orbit 视角，
  继续拖拽 / WASD 都正常。

第一人称期间相机仍会随选手每帧移动（那正是第一人称），但**没有任何手动相机
输入**能改变它。选手阵亡时自动退出并恢复自由镜头。

### 4.13.2 准星和 HUD

* 准星用 DOM 叠在视口正中。第一人称相机就是按这个选手的 `yaw/pitch` 摆的，
  所以屏幕中心 = 他的瞄准方向，不需要再做一次 FOV 投影。
* HUD 在准星下方（视口底部居中）：生命值 + 血条、护甲、是否有头盔、当前武器、
  背包装备（`inventory` 去掉当前武器并去重）、选手名和队伍。
* 数值每帧从 `getPlayerState()` 的当前状态刷新，和右侧详情 / 左侧血条同源。

### 4.13.3 yaw 跨 ±180 时不能直接线性插值

`getPlayerState()` 按 `currentTime` 在相邻采样点之间插值。位置用普通 `lerp` 是对的，
**yaw 不行**：它在数据里是 `[-180, 180]`（demo 的 `m_angEyeAngles` 就是这个范围），
一次连续转身跨过 seam 时相邻两点的数值看起来差 350°+，普通 lerp 会绕远路。

实测（`app/data/csz/aurora-vs-vitality-m1-anubis__ecd40737.csz` 第 1 回合 ZywOo，
all-tick 64 Hz）：

| 采样点 | yaw | 真实变化 |
|---|---|---|
| 78.2656 s | 178.12° | |
| 78.2812 s | -175.54° | **+6.34°**（继续右转） |
| 中点（普通 lerp） | **1.29°** | 偏了 **176.8°** |

60 fps 回放这一段时，普通 lerp 会给出 `t=80.867 s → yaw -11.74°`，而逐帧真值是
`≈160.9°` —— 一帧看向背后再回来，就是"抽搐"。同一回合 80.56–81.02 s 里连续跨
seam **四次**，所以看起来是半秒的抽动。逐帧看的工具（`training_data_visualizer`
的第一人称）不插值，所以那边一直是正常的。

现在 `replay-core.js` 的 `lerpAngle()` 取差值折回 `[-180, 180)` 再乘 `t`（最短弧），
同一段的帧间角位移回到 9.25°（真实的快速甩枪），和逐帧真值的差 ≤ 半个 tick 的转角。
`pitch` 不用改：它被夹在 ±89°，没有 seam。

```bash
node visualizer/tests/test_angle_wrap.mjs      # 纯 node，不需要服务器 / demo
```

## 4.14 地图材质颜色（把 CS2 的材质搬回灰模）

> ⏸ **已停用（2026-11，默认关闭）**。这一节记的是"把材质色烘回灰模"的做法和踩的坑，
> 代码都还在，但 `map-loader.js` 的 `BAKED_COLORS` 默认 `false`，地图回到
> `setupMapMaterials()` 的水泥灰 —— 也就是这个功能加进来之前的样子。
>
> 停用原因：这套配色是照着"带贴图和材质的完整模型"设计的，套在 Open3D 导出的**简化
> 碰撞几何**上不划算：
>
> * 8 色板下同一面墙上的面本来就会落到同一个色号，真正显形的差异在**逐面法线**
>   （实测重合面之间差到 100° 以上），于是法线也得一起烘、还得做"重合/重叠面统一"，
>   两步都只能**掩盖**深度争夺，不能消除；
> * 一份旁车 7–21 MB/张图，八张图 140 MB，且每次 OBJ 变了都要重烘；
> * 收益只是"大概色块"，而它引入的闪烁问题要花几何层去重（按平面聚类 + 2D 覆盖裁面）
>   才能根治，那是另一个量级的工程。
>
> 想再打开：URL 加 `?mapcolors=1`（`?mapcolors=0` 显式关；也可以在 localStorage 里
> 设 `mapColors=1`）。旁车文件还在 `maps/optimized_obj_files/*.colors.bin`（已加进
> `.gitignore`），确认不要了可以直接删掉，删掉之后这个功能就是 404 → 静默退回水泥灰。

地图 OBJ 是 Open3D 导出的**纯几何**：`v` 行 211 万条，`vt` / `vn` / `usemtl` / `mtllib`
**各 0 条**。所以"地图是白的"不是材质没设，而是每个三角形都不知道自己是什么表面，
`map-loader.js` 只能按法线糊一层水泥灰，再叠点噪声假装混凝土。

材质在游戏里一点没丢。`game/csgo/maps/de_inferno.vpk` 里的 `maps/de_inferno/worldnodes/`
是 784 个聚合网格，带 `TEXCOORD_0` 和材质：**779 个节点只有 1 个材质**，全图 **327 个
.vmat、243 张 base color 贴图**，合计 **8,419,800 个三角形**（其中约 250 个节点是贴花/
覆盖层，参与回投影的 opaque 部分是 303 个材质 / 8,395,911 个三角形）。关键是两套几何
**在同一个坐标系里** —— 导出的世界 bbox `[-70.80,-6.80,-90.10] ~ [107.80,39.00,100.60]`，
OBJ 是 `[-70.79,-6.78,-90.13] ~ [107.81,38.98,100.60]`，差 1 cm，所以不需要拟合任何变换。

### 4.14.1 怎么烘的：按位置把颜色"回投影"回去

烘焙是一次性离线的（4–7 分钟/张图，de_cache 最慢 6.7 分钟）。**烘焙脚本未随仓库发布**，

```bash
# 离线烘焙（脚本未随仓库发布）：bake_map_colors --map de_inferno
#   [ref] 784 个 worldnode → 785 个 GLB（带 UV + 材质），263 s
#   [ref] 8,395,911 triangles, 303 materials, 220 colour maps   ← 贴花已剔除
#   [tex] 300/303 materials have a base colour map
#   [match] {"faces":3292872,"matched":3292857,"matched_pct":100.0,
#            "distance_m":{"median":0.0048,"p99":0.1566,"max":2.2475}}
#   [smooth] 115,583/3,292,872 faces repainted from their neighbourhood
#   [flat]   301 materials -> 301 flat colours
#   [palette] 1497 -> 8 colours
#   [coincident] 42,772 duplicate face groups, 72,140 faces made identical
#   [out] maps/optimized_obj_files/de_inferno.colors.bin (19.76 MB, v2, 8 colours)
```

1. **导出世界几何**：`Source2Viewer-CLI -f "maps/<map>/worldnodes/" -d --gltf_export_format glb
   --gltf_export_materials`。每个 face set 带一个 `material`（vmat 全路径）和它的
   `baseColorTexture`，贴图由 CLI 顺手落成 PNG。
   ⚠️ **不能直接 `-d` 一个 `.vmat_c`**：仓库里这版 CLI 对 CS2 当前 shader
   （`vcsFileVersion 72`）会抛 `UnexpectedMagicException`，只有 glTF 这条路能绕过去。
2. **颜色表**：2048² 的贴图降到 256²，按材质存成一张 LUT（303 × 256² × 3 ≈ 60 MB，进程内）。
   同一个文件被多个材质引用（`barrel_kit_01` 有五个 tint/blend 变体共用一张图），所以
   要**先按文件名去重再删**，不能在循环里用完就 unlink。
3. **回投影**：对 OBJ 的 3,292,872 个面取重心，用 KD-tree（8.4M 个原始三角形重心）
   找最近的原始三角形，要求法线同向（`|dot| ≥ 0.7`，墙的内外两面共用同一个表面），
   命中后继承它的材质、按它的 UV 在贴图上采一个色。
   实测**99.9996% 命中，中位距离 4.8 mm，p99 15.6 cm** —— 这个分布本身就说明 OBJ 就是
   这套几何的减面版，不是"两套勉强对齐的模型"。
   **贴花/覆盖层不参与**（`materials/**/decals/`、`**/overlay/`）：它们在游戏里是半透明的
   独立几何、贴着地面几毫米，搬成不透明颜色就是地砖上撒了一层杂色三角。
4. **邻域众数**：一个三角形经常横跨两三种材质（路缘、土带），最近匹配就会逐面跳。
   在 OBJ 自己的面重心上查 5 个邻居（0.35 m），取**材质众数**，把那个邻居的颜色搬过来 ——
   实测改掉 3.5% 的面，跳变消失，边界只推移 ≤ 0.35 m。
5. **按材质压平**：每个材质算一个**面积加权平均色**（在线性空间里平均，见下面的坑）。
   这一步才真正消掉"贴图本身的斑驳"——同一块地砖上明暗土块被合成一个色。
6. **压色板 + 平滑法线**：OkLab 里 k 均值压到 **8 色**；同时按顶点累加面法线、带 60°
   折角保护，算出**每面的平滑法线**（int8，3 字节/面）—— 平地上几千个三角形的法线差
   1~2°，光照下就是一片明暗小三角，这是压完色之后剩下最难看的那个东西。
7. **重合面统一**（`unify_coincident_faces`）：OBJ 是碰撞网格（brush soup），同一块表面
   经常由两个 brush 各出一份，**顶点位置完全重合**。两份的深度也完全相同，逐像素谁赢
   取决于光栅化/浮点的末位误差 —— 画面上就是一片横向细条纹（z-fighting），镜头一动就闪。
   两份涂同一个颜色时看不出来，但"逐面平滑法线"是按各自的面邻域算的，两份会差 1°~30°，
   光照下差几级，于是这份 z-fighting 就露出来了（**色板压到 8 色也救不了，差异在光照**）。
   做法：按顶点位置（1 mm）分组，组内取同向（夹角 < 30°，背靠背的两份不算）的面，
   统一成"面积最大的那个面的颜色 + 面积加权平均法线"。de_inferno 实测 42,772 组、
   72,140 个面（其中 45,467 个是多余副本）。`--no-unify` 可关掉。
8. **覆盖面统一**（`unify_overlapping_faces`）：上一步只认"顶点完全重合"。brush soup 里
   更常见的是差 1~2 mm 的两层笔刷，或者**同一个四边形被另一种对角线切开** —— 顶点对不上，
   但两个三角形盖住了同一片区域，深度只差零点几毫米。判据：几何法线夹角 < 20°、重心到对方
   平面 < 2 mm，且一个面的重心落在另一个三角形内（两者重心几乎重合也算）。每个面跟随
   "盖住它的面里面积最大的那个"，形成只指向更大面积的森林（无环，也不会把一整块地板
   连成一片），每簇取面积最大面的颜色、簇内朝向自己几何法线的平滑法线按面积加权平均。
   de_inferno 实测 149,155 对、49,755 簇、127,753 个面被改成同一个样子 —— 其中**颜色一个
   面都没变**（8 色板下两份本来就是同一个色号，挑的又都是面积最大的那个面的颜色），
   改的全是**法线**：70,006 个面变了 1° 以上，25,586 个超过 10°，5,557 个超过 30°。
   `--no-overlap` 可关掉。
9. **落盘**：`MCLR` + u16 版本 + u16 flags（= 色板大小）+ u32 面数 + 每面 3 字节 sRGB
   + 每面 3 字节 int8 法线，共 19.76 MB。

面数必须和 OBJ 的 `f` 行数**逐个对上**：这个文件是按 `f` 行顺序存的，错一个面就整张
图错位一格颜色，不会崩、只会"看起来有点脏"。

**改了 OBJ 就要重跑同一条烘焙**（重新减面、删东西、挪顶点都算）—— 烘焙脚本未随仓库发布，
`.colors.bin` 本身也是 gitignore 的本地产物，所以这一步只在你自己改过地图时才需要。

* 不用加 `--force`：缓存按**文件签名**失效，OBJ 改过就自动重新解析（CS2 那边的
  `reference.npz` 只在游戏 VPK 变了才重建，所以热缓存下整张图 ~30 秒）。
* 面数变了前端会**直接拒用**（`stale-<文件里的>-vs-<网格的>`），退回水泥灰；
  **面数没变但几何变了是不会被发现的** —— 颜色会整体错位，所以别指望这个检查，
  改过就重烘。
* 烘焙脚本按 OBJLoader 的规则把多边形（四边形等）扇面三角化，所以带四边形的 OBJ
  也能对上；`test_map_colors.py` 数面时同样按 `n-2` 折算。

⚠️ **平均颜色必须在线性空间里做**。第一版直接对 sRGB 求平均，整张图偏亮发白（sRGB 是
非线性的，"灰泥 + 污渍"的平均会被抬成浅米色）。改成 `srgb → linear → 平均 → sRGB` 才对。

### 4.14.2 运行时只多了一个 fetch

> ⏸ 现在默认关着（`BAKED_COLORS = false`），这一 fetch 不会发生，地图停在水泥灰。
> 打开方式见本节开头。下面写的是"打开时"的行为。

`map-loader.js` 里 `setupMapMaterials()` 之后 `await applyBakedColors()`：

* `GET /api/map/<name>/colors` → 校验 magic / 版本 / 长度 / **面数 == 网格面数**；
* 通过就把每面的 3 个角写成同一个颜色（`color` 属性），sRGB → 线性走 256 项查表
  （330 万个面各 `new THREE.Color()` 太慢），实测 **20~300 ms**；
* v2 的旁车还带平滑法线，同一趟循环里写进 `normal` 属性 —— `computeVertexNormals()`
  先算出来的逐面法线会被覆盖掉；
* 任何一项不通过（没烘、OBJ 换过版本、面数对不上）就**静默退回水泥灰**，地图照常能看。
  失败原因记在 `__v5.mapColors.reason` 里（`http-404` / `stale-…` / `bad-header-…`）。

`mmColor`（小地图的高程灰阶）**没动**：小地图要的是"看得出高低"，真材质俯视图反而糊成
一片，所以切小地图时仍然把 `color` 换成 `mmColor`。

### 4.14.3 已知取舍

* **是"每材质一个颜色 + 8 色板"，不是贴图**。301 个材质各一个平均色，再 k 均值压到
  8 色。近看是干净的色块（这本来就是想要的效果：不想要"细碎的三角形"），代价是丢掉
  了贴图上的砖缝、木纹这些细节。想要真贴图得再做一个 UV 图集（回投影的中间产物已经
  够插值出 UV）。
* **8 色会把绿色防水布合掉**。inferno A 点那种绿色篷布是"小而艳"的色块，k 均值按面积
  分配色号，8 色时没有色号给它，会被并进橄榄灰。想要回来就 `--palette 12`（12 色能保住
  它，见 §4.14.4 的对比图）；`--palette 0` 则是 301 个材质各自一个色、完全不压。
* **比游戏里"平"**。CS2 的观感一半来自烘焙 lightmap，这里只搬 albedo，用现有的三盏灯照，
  整体偏亮。`csgo_environment_blend` 那类**两层混合**材质只取了第一层，所以路面上少了
  第二层的泥土斑。要更接近就在烘焙时乘一个亮度系数，或者把第二层按顶点色混进去。
* **游戏更新地图后会失配**。颜色取自当前版本的 vpk，地图改版要重跑一次烘焙；重跑是幂等的，
  而且和"你手动删过树"无关 —— 匹配是纯几何的，删掉的面没有对应关系，剩下的照常上色。
* **很白的图会更白**（de_nuke 实测）：它的 albedo 本身就是灰白金属板，而这里的三盏灯
  加起来能到 2.3 倍，ACES 之后基本饱和。想压回来就调 `map-loader.js` 里地图材质的
  `color` 系数，或在使用前对烘好的颜色乘一个统一亮度。
* **重合面只修了两类**。`unify_coincident_faces` 管"顶点完全重合"，`unify_overlapping_faces`
  管"2 mm 内互相盖住"（含换三角化）。没管的：(a) 相交但不共面的两层笔刷，只在交线附近
  闪一条细线；(b) 差 2 mm 以上、要到几十米外深度精度才分不开的擦边重合；(c) 真正的几何
  去重（按平面 + 2D 覆盖裁面）—— 那要重写 130 MB 的 OBJ。判断手上这张图是不是 z-fighting：
  把摄像机的 `near` 从 0.1 调到 2（`camera.near = 2`）—— 深度精度一下子好 20 倍，条纹明显
  变化或消失就是 z-fighting，跟颜色/色板无关。注意**同色还不够**：法线不同，光照就不一样，
  两份还是看得出来，所以这一步必须颜色 + 法线一起统一。
* **三角形边界还会剩一点**：颜色是"每面一个"，所以材质分界必然是折线；法线也是"每面
  一个"，弯面/被减面噪声弄皱的平面上相邻面仍会差 1~3°，远看是极淡的明暗三角。
  要彻底消掉得改成"每顶点颜色 + 每顶点法线"（插值），旁车格式要加一版。

8 色和 12 色的差别（同机位，左边是现在用的 8 色）：绿色篷布在 8 色下被并进橄榄灰，
其余几乎看不出区别。

## 4.15 AI 预测：把 `aim` / `spatial_prediction` 接到回放页上

底部两个开关（**AI 预测面板**、**AI 对枪**）打开之后，模型的结果直接画在 3D 场景里。
数据来自 `app/ai`（`GET /api/ai/round/<idx>?progress=1`，见 `app/README.md` 和
`app/ai/service.py` 的模块 docstring）；这个仓库的 `visualizer/` 只负责画。

### 4.15.1 画的是什么

```
          A ●━━━━━━━━━━━━━━━━━┿━━━━━━━━━━━━━━━● B
            （红，P(A 赢) 越低越红）  （绿，P(B 赢) 越高越绿）
             ▲                                ▲
     这场对枪会死的那个                这场对枪杀人的那个
```

3D 里**只有几何和颜色，一个数字都不写**：头顶原先挂的存活百分比、弧线上的游标点
和数字全撤了，数字只出现在左下角的选手指标表里。同一份数在两处维护必然漂移，
而且头顶一排文字挡人、挡枪线、挡烟火 —— 要读数看表格，"偏不偏"看两段弧线谁更绿。

* **弧线**：两顶之间一条二次贝塞尔（中点抬高 `0.45 + 0.34 × 距离`，封顶 2.4 个单位
  ≈ 2.4 m —— 真实击杀的对枪常有 20 m 开外，不封顶弧会顶出画面），画成虚线
  （48 段取样、隔一段画一段），`depthTest:false`，穿墙也看得见。
* **只在死前 3 秒出现**：服务端只对"死前 3 秒 → 受害者最后一个活帧"这一段给 aim
  预测，所以场上没有对枪就没有弧线；窗口开头 0.35 秒淡入（`duel.fade`）。两端用的
  是这一回合**真实的击杀双方**（A = 受害者、B = 击杀者），不是模型猜的一对 ——
  "谁即将被打死"由 `next_death` / `next_kill` 在指标表里回答。**回合结束那一枪
  （打死最后一个敌人、回合立刻结束）也在内**：服务端把它挂在最后一帧上（受害者在
  那一帧还活着），否则 63% 的回合会缺最后一场对枪（`app/ai/service.py::_round_kills`）。
* **从中间切成两段**：切点 = `p = P(A 赢)`，从 A 端往 B 端量。**没有游标球** ——
  两段颜色的分界就是那个位置：A 侧的段越红，A 越可能死；B 侧的段越绿，B 越可能赢。
  具体数字在表格「对枪」那一格。
* **颜色**：两侧各按"那一侧那个人的胜率"上色，0% 红 → 50% 黑 → 100% 绿
  （`probColor()`）。50% 的黑线在暗地图上就是"看不出偏向"，这正是要的。
* **只此一项，没有光环**：脚底下的存活光环（`RingGeometry` + shader 裁圆周）和头顶的
  百分比一起撤了 —— 存活率在左下表格第 1 列，3D 里不画第二样东西。
* **顶部面板（只有赢面）**：CT / T 各自赢下这一回合的概率 + 一根两段条（正中一条
  50% 刻度线），外加"分析中 / 缓存 / 新算 16.3 s"和用的哪两份权重。**不放下一杀 /
  下一死** —— 那是选手级的量，全在左下表格里。**两个百分比自己也能点**：和表格里
  的数字一样打开整回合的胜率曲线（`win_ct` / `win_t`，T = 100% − CT），点曲线任意
  一点跳到那一刻；它不属于某个人，所以**跳转不锁镜头**。
* **左下角选手指标表**（`#ai-table`）：一人一行、五格概率 —— 存活 / 可击杀 / 下次
  击杀 / 下次被击杀 / 对枪。行顺序固定（先 CT 后 T，按槽位），不按概率排序（每帧跳动
  的排行榜没法看）；死掉的人整行变淡、概率显示 `—`；当前这场对枪的两个人带 `⚔`，
  对枪格是各自那一侧的胜率（两人加起来 100%），悬停那一格能看到「A vs B」——
  弧线上不再写名字了，这是"这两个人是谁"的唯一文字出处。
* **表上三种交互**（`.ai-table` 整块 `pointer-events:none`，只有列头 / 名字 / 数字
  自己接收鼠标；行间那 4px 缝隙仍然能把拖拽让给 3D 视口）：
  * **悬停列头** → `#ai-tip` 说明这一项在预测什么、该怎么读。六个列头（含「选手」）
    + 顶部两个胜率各有一段文案，都放在 `main.js::AI_METRIC_HELP` 里，和曲线卡标题
    共用同一份名字。
  * **点名字** → 和点左边选手卡片一样：展开卡片、镜头飞过去并跟随
    （`focusPlayerFromAi()`）。和卡片唯一的区别是这里不会"再点一次收起" ——
    点名字的意图是跳过去，不是取消。
  * **点数字** → 表格正上方长出 `#ai-chart`（`ai-chart.js`）：这一项整回合 4 Hz 的
    折线，死掉的采样点断开、标一条红色虚线，白线是播放头。**点曲线上任意一点 =
    暂停 + `seekTo()` + 锁定这个选手**，从"看到他存活率开始掉"到"看那一刻他站哪"
    只差一次点击；`✕` 或 `Esc` 关掉。点「对枪」那一格没有曲线 —— aim 只在死前
    3 秒里有值，画一整回合是假数据。数据不用再请求：曲线就是 `aiRound.spatial`
    里的那一列，和表格里的数字永远同源。
* **顶部胜率的曲线**：同一张 `#ai-chart`，画 `win_ct` / `win_t` 整回合（两条互补）。
  点百分比打开、点曲线上任意一点 = 暂停 + `seekTo()`，但**不选中 / 不锁定任何
  选手**（`player = -1`）：用户可能正跟着某个人看，跳一下胜率不该把他甩掉。胜率
  没有"阵亡"概念，所以这条曲线没有红色虚线。
* **进度条**：冷分析一次十几秒，所以面板里有一条进度条：阶段 + 百分比 + 已用时。
  阶段文本由服务端给（"玩家特征 3/10…"、"两两遮挡 2048/6828 帧…"、"逐帧推理
  256/427…"），前端每帧往目标值靠一点（`updateAiProgress()`），不会一跳一跳。

### 4.15.2 为什么是 4 Hz 插值

服务端默认每 **16 个采样点**给一个预测点（逐 tick 的 demo 就是 4 Hz）。前端
`aiFrameAt()` 在相邻两个点之间线性插值，所以 60 fps 的回放不会一跳一跳；
`next_death` / `next_kill` 是**逐人**取插值后的那一项（每一列都是同一个 softmax
的第 p 项，插值是有意义的），而对枪的两个人只有在相邻两点是**同一对**时才插值
胜率，否则直接吸附到最近那个点 —— 否则会出现"A 的 40% 和 B 的 60%"被插成 50%
这种假数据。

### 4.15.3 为什么模型在 `app/`、画在 `visualizer/`

预测要读"当前回放会话"（`_session["data"]`），所以路由放在 `app/ai/api.py`，只向
`visualizer/server.py` 要一个只读快照（`session_snapshot()`）。依赖方向仍然是
`app → visualizer`：单独跑 `python visualizer/server.py` 时那两个路由不存在，
开关会被 `/api/ai/status` 的失败挡掉（`loadAiStatus()` 会把它们禁用并在 title 里写原因）。

torch / numba 都只在**第一次点开关**时 import（`app/ai/models.py` 的 `Bundle.load()`），
页面启动不受影响。用的是哪两份权重由 `app/ai/models.py::PINNED_WEIGHTS` 写死
（扁平的 `<run>.pt` + 同名 `<run>.yaml`，由 `scripts/export_weights.py` 从训练产物
抽出，不含优化器状态）；面板里那行小字是 run 名，鼠标悬停显示具体的
文件名 —— 换版本就改那一行，刷新页面即生效。

页面一打开就会调 `/api/ai/status`，服务端顺手在**后台线程**里把 numba 遮挡内核和
当前这张图的 BVH 先编出来（`service.warmup()`，第一次要 ~10 s）—— 这些和用户点哪个
回合无关，不该算在"点一下"的头上。

### 4.15.4 代价

| 场景 | 实测（RTX 3090，6800 采样 / 106 s 的回合） |
| --- | --- |
| 进程里第一次分析（含地图 BVH + numba 编译） | **15~25 s**（有进度条） |
| 预热过 / 之后的回合 | 7~10 s（特征 4.2 s + 遮挡 3.4 s + 两路前向 0.9 s） |
| 同一个回合再点 | **3~70 ms**（读 `app/data/ai/` 里的 JSON） |

第一次点开关会弹一条 toast「AI 分析中（进度见上方面板）」，面板右上角显示
"分析中 / 缓存 / 新算 16.3 s"。切回合时上一份预测直接作废、**在飞的请求 abort**，
再按开关状态重新拉（服务端按回合缓存）。

### 4.15.6 已知限制

* **只认训练用的 8 张图**：坐标归一化对未知地图是静默失真的，所以 `app/ai/features.py`
  直接拒绝，不要拿它猜。
* **只认逐 tick 的 `.csz`**：模型的时间位置是 `seconds × 64`；按 stride / interval 抽的
  文件里"4 秒窗口"会跨几十秒，喂进去不在分布里。用 `interval` 抽的 demo 想看 AI，
  得按「每个 tick」重抽一次。
* **对枪用的是已知结果**（谁杀谁来自 `.csz` 的击杀事件）：这是**回放分析**，不是
  实时预测 —— 弧线回答的是"这一枪之前模型觉得谁会赢"，不是"谁会去打谁"。
* **`aim` 的窗口只有 3 秒**：一场超过 3 秒的拉锯只显示最后 3 秒；更早的部分没有
  弧线（训练分布是死前 4 秒内的每一帧，3 秒是保守取值）。
* **两个头可以打架**：`spatial` 说"下一个死的是 A"，`aim` 却可能说"A 单挑有 58%" ——
  这不是 bug：`aim` 只回答**这两个人之间**谁赢，A 完全可能是被第三个人打死、或者
  被队友补枪。弧线读的是"单挑胜率"，不是"谁死"。要看"谁死"看指标表的「下次被击杀」。
* **补枪时只画一场**：两场对枪的窗口重叠时（A 死后 0.3 秒 B 被补），归"死得最早"的
  那场；后一场如果连一个 4 Hz 采样点都没剩下，整场就不出现在 payload 里。
* **死人不画**：对枪的一方死了（或者其中一个人已经阵亡），弧线立刻隐藏（不是停在
  最后一个值）。
* **回合结束那一枪的样本是后补的**：`tasks/_util.py::late_kills()` 现在会把这一枪补进
  造数（`aim` 多一条样本、`spatial_prediction` 的 `alive_end` 指向它），推理端同样把
  它挂到最后一帧上去问模型（`app/ai/service.py::_round_kills`）。但**仓库里已有的
  数据集 / 权重**是补之前造的，要让模型真正见过它，得重跑 `prepare` 再重训。

## 4.16 中英双语（顶栏的 `中文 | EN`）

四个页面共用一套运行时，目录是 `visualizer/static/js/i18n/`：

* **文案表按页面分文件**：`common.js`（导航 / 文档标题 / 通用按钮）、
  `replay.js`、`library.js`、`players.js`（玩家索引 + 档案）。每个键都有 zh 和 en
  两份，键集合必须一致；`index.js` 只负责选语言、取词、刷 DOM、画顶栏开关。
* **HTML 里原文照旧写中文**，另外挂 `data-i18n`（textContent）、
  `data-i18n-html`（带 `<b>` / `<br>` 的）、`data-i18n-title`、
  `data-i18n-placeholder`、`data-i18n-aria-label`。这样没有 JS 时页面仍是完整的
  中文，默认语言也不依赖脚本。
* **JS 里会进 DOM 的字**用 `t('key', { n })`（占位符 `{n}` / `{msg}`）。注释和
  `console.*` 不翻 —— 那是写给开发者看的。
* **语言优先级**：`?lang=` > `localStorage['csnet.lang']` > **中文**。不做浏览器
  语言自动判断：产品是中文语境，`en-US` 的浏览器自动进英文反而多一步；英文用户点
  右上角 EN，选择会记住，分享链接可以带 `?lang=en`。
* **切换 = 记住 + 刷新**。页面里大量文案是渲染时一次性拼出来的（选手卡片、统计
  矩阵、指标表、AI 释义），逐个重渲染等于把每个页面再写一遍，漏一处就是"一半中文
  一半英文"；语言是低频操作，刷新最不容易错。
* **顶栏开关由 JS 插进 `.tb-actions`**，四个模板只多一行 import —— 一份代码保证
  四页长得一样，也不会漏掉某一页。样式在共用的 `topbar.css`。
* **服务端返回的数据在前端翻显示名**：平台（`本地` / `5E` / `完美` / `官匹`）、
  存储目录（`csz` / `thumbs` / `avatars` / `recycle` / `db`）、统计里的
  `队伍 A/B`。写回接口和 class 名的仍是原始值，翻译只影响显示。

## 5. 数据是怎么送到浏览器的（为什么要这么设计）

all-tick 下**整场**玩家列的 JSON 是 **162 MB**（实测），整包发给前端不现实。
所以按回合切：

```
POST /api/load        → 后台解析，返回 job_id
GET  /api/load/status → 进度（step / elapsed），done 时带一次 summary
GET  /api/session     → 摘要：地图 / 玩家 / 武器表 / 地名表 / 回排名 / 采样方式 / 统计
GET  /api/round/<i>   → 单个回合的**紧凑载荷**
GET  /api/download    → .csz 原文件
POST /api/clear       → 丢掉服务端会话
```

单个回合载荷（最大回合 = 7875 采样，**6.7 MB**）里：

| 内容 | 编码 |
|---|---|
| `ticks` | base64 Int32 |
| 玩家 `x y z yaw pitch v flash flash_alpha` | base64 **Float32** |
| 玩家 `hp armor weapon place` | base64 **Int16** |
| 玩家 `shots footsteps jump land crouch` | base64 **Uint8** |
| 玩家 `helmet defuser alive on_ground crouching` | 1 个字节打包 5 位 → 前端展开成 5 条 Uint8 列 |
| 玩家 `inventory` | **稀疏**（只在变化时记 `{i, v}`），播放时二分查 |
| 玩家 `spotted` | 同上，**稀疏** `{i, v}`；`v` 是"能看到这个玩家的敌人"编号 |
| `bomb_planted/dropped/position` | Uint8 / Float32（没拿在手上 = NaN） |
| `events` | 原样（`smokes`/`infernos` 的 `s0/s1` 归一化成 `ts/te` 便于区间过滤） |
| `fire[]` | 原样（格子坐标/法向/燃烧位，很小，全场 1.3 MB） |
| `smoke[]` | journal 变更的 `data` 转 **base64**（全场 1.2 MB） |

前端 `replay-core.js` 把 base64 直接 `new Float32Array(bytes.buffer, 0, n)` 零拷贝成 typed array，
所以 10 个玩家 × 8 千采样也只是一个普通数组的量级，不是 8 万个 JS number。
回合按需拉取并缓存，来回切回合不重复请求。

## 8. 已知限制

* **火/烟需要 demoinfocs-golang v5.3.0**：烟和火的原始数据来自 `tools/demo_extract/sidechannel_go`
  这个 Go 辅助程序，它要求 `demoinfocs-golang/v5`。用 v4（哪怕是最后一版 v4.5.1）
  在较新的 demo 上会崩（`unable to find existing entity` → `unexpected team` 乱码 → 整场提取失败），
  而且**不是 demo 坏了**：同一份 demo 的玩家数据 demoparser2 能正常读出来。
  v5.2.0 更阴：**2026-11-11 之后录的 demo 它解不开，却不报错** —— 写出来的 `.csz` 里
  `fire` / `smoke` 全空（`infernos=0 smokes=0 voxel_capacity=0`），表现就是回放页上
  没有烟也没有火。这种情况 `extract.py` 现在会拿事件流对账并直接失败，但根治仍是升到
  **v5.3.0** 后重新编译：`bash tools/demo_extract/build_sidechannel.sh`。
  详见 `tools/demo_extract/README.md` §5「依赖版本」。
* **少数烟雾没有引爆点，跳过不画**：`demo_extract` 的 `detonation` 是按"实体 id + 最近 tick"
  匹配 `smokegrenade_detonate` 事件得来的，匹配不到就是 `null`（实测 550 MB 的 de_inferno 上
  170 个烟雾里有 1 个，在最后一个回合 —— demo 在烟雾结束前就录完了）。
  没有引爆点就没法把体素栅格放进世界坐标（`world = detonation + (grid−15.5)×12`），
  所以**跳过不渲染**。
  不能拿 `[0,0,0]` 兜底 —— 那会在地图原点凭空多出一团雾，比不画更糟。
* **地图的材质色是烘出来的，不是实时读的**：`maps/optimized_obj_files/<map>.colors.bin`
  由离线资产管线从 CS2 安装里回投影生成（§4.14，9.4 MB/张；脚本未随仓库发布）。
  *没有这个文件*时地图退回 `map-loader.js` 的水泥灰顶点色 —— 仍然能看，只是灰的。
  它和 `*.obj` 一样是 gitignore 的本地产物，换机器/游戏更新后要重跑一次烘焙。
* **地图目录默认指向隔壁 `cs-net`**：本仓库没有 `maps/`，`server.py` 会去
  `../cs-net/maps/optimized_obj_files` 找。想把地图并进来就 `cp -r` 一份，或一直用 `--maps-dir`。
* **`spotted`（谁看得见谁）现在送到前端了**，但是**稀疏**传的（只在变化时记
  `{i, v}`，一整场 24 回合只有 740 个变化点），用来画 §4.8 的眼睛图标。
  逐 tick 原样发才会肥（10 人 × 几千采样），别那么干。
  要用完整矩阵就直接读 `.csz`（`recipes.spotted_multihot(rnd)`）。
* **火焰的 `parent`（蔓延树）只提取了没画**：数据在 `fire[].changes[].parent` 里，想做蔓延可视化可以直接用。
* **体素容量**：单个烟雾最多画 12288 个体素（凸包重建后实测最多 6408），超出会截断并在控制台告警。
* **下蹲需要 v7 的 `.csz`**：v6 文件里没有 `crouch` 列，前端读不到就当成 0（站立）——
  碰撞盒恒为 72、眼睛恒为 64.09，**不会报错**。`outputs/` 里现有的 `.csz` 都是 v6 的，
  要看到下蹲得重新提取一次（`python -m demo_extract.cli match.dem -o out.csz`）。
  面板里「下蹲 crouch」那行会直接写「无（v6 文件）」，用来一眼分辨。
* **瞄准射线的"打人"是碰撞盒，不是 hitbox**：红色射线只说明视线进入了对方的**移动碰撞盒**
  （32×32×72/54），这是可射击判定区的**超集**。真正的 hitbox 骨骼绑定、随姿态变形，demo 里没有。
  另外死人不挡子弹（不参与截断），队友会挡。
* **子弹曳光是理想直线，不是真实弹道**：demo 里没有子弹实体，`fire_bullets` 那种
  「origin + angles + seed + spread」没有提取，所以方向只有 yaw/pitch，遮挡只有
  「眼睛 → 第一个碰撞盒/三角形」——**没有 spread / 穿透 / 距离衰减**。
  曳光停在哪只说明"那条视线被什么挡住了"，不等于"这一枪打中了什么"。详见 §4.7.1。
* **摆腿是"朝向对齐"的，横向平移（strafe）会滑步**：小人本身按 yaw 转，腿沿**面朝方向**
  前后摆。CS 里横向平移很常见，那时脚其实是在往侧面滑 —— 但摆的频率仍然跟真实走过的
  距离走。要做对得让摆轴垂直于**移动**方向（而不是面朝方向），那需要再存一个逐采样的
  移动方向。
* **步态只对 v6+ 有意义**：相位吃 (x, y) 位移、摆幅吃 `v` 列，都是 v6 就有的列。
  但空中判定用 `on_ground`，v6 之前没有这一列 —— 老文件会一直当成在地面。
* **地图 BVH 要 268 ms 建一次**：第一次打开「瞄准射线」时建（823k 三角形），
  那一刻按钮会置灰。建好之前射线只截断到玩家，不会报错。
* **站立足眼高 64.0938 HU 是文档值，不是实测值**：CS2 没有网络化任何视点偏移字段，
  demo 里拿不到绝对值（详见 `tools/demo_extract/API.md` §4.12）。demo 能精确给的是
  **18 HU 的行程**。要改成 64.000 就改 `replay-core.js` 里那一个常数，画面差别 2.4 mm。
* **英文界面里服务端文案仍是中文**：`/api/*` 的错误提示、后台任务的 `title` / `step`
  （`app/api.py`、`app/jobs.py`、`visualizer/server.py`）没有接 i18n —— 它们只在失败
  toast 和任务抽屉里出现。页面本身（四个页面的模板 + JS）已全部走 `i18n/`（§4.16）。
