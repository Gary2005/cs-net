## 0. 名词解释（先看这节）

| 名词 | 什么意思 |
|---|---|
| **`.dem` / demo 文件** | CS2 的比赛录制文件。里面记录了整场比赛**每一帧**的全部游戏状态，而不只是画面。所以它能用来做数据分析和训练 AI，不只是看回放。 |
| **tick（帧）** | 游戏逻辑的最小时间步。CS2 服务器是 **64 tick/秒**（我实测确认：`game_time` 的斜率正好是 1/64）。所以一场 24 回合的比赛大约 16.7 万 tick。 |
| **实体（entity）** | 游戏世界里的一个对象：一个玩家、一颗烟雾弹、一个燃烧瓶、一扇门，都是一个"实体"。每个实体有个编号。 |
| **实体属性表 / sendtable** | 游戏把每个实体的状态表示成「属性名 → 值」的清单，每 tick 更新一次。你可以把它想成一张巨大的表格：**行是时间（tick），列是属性**（比如"玩家3的X坐标"）。这是 demo 里最主要的可读数据层。 |
| **游戏事件（game event）** | 游戏另外单独记录的一类数据：离散的、有意义的事情，比如「某人开枪了」「炸弹被安放了」「有人死了」。**它和逐 tick 属性表是两条不同的数据通道**，字段也完全不同。 |
| **网络消息（packet 层 / 数据包）** | demo 文件里还有第三层数据：服务器依次发给客户端的数据包原文。有些信息只存在于这一层，**属性表里根本没有**。后文提到的 `svc_UserCmds`（玩家操作指令）就是这一层的。 |
| **protobuf** | Google 的一种二进制数据格式，常用来打包网络消息。要读它得先按它的规则解包，不能直接当文本看。 |
| **位掩码（bitmask）** | 用一个整数的**每一位**表示一个开关。比如第 0 位代表"W 键按下"，第 1 位代表"A 键按下"。这样一个整数就能同时表示 13 个键的状态。 |
| **Morton 编码（Z 序曲线）** | 一种把三维坐标 `(x, y, z)` 压成**一个整数**的技巧：把三个坐标的二进制位交错排列。好处是一个一维数组就能表示三维空间，而且空间上相邻的点，索引号也接近。 |
| **洪泛填充（flood fill）** | 从一个起点往外扩散，把所有连通的位置标记出来。这里用来区分"被烟雾边界围住的内部"和"外面的空气"。**实测在烟雾体素上失效，本项目已弃用并删除**（见下方更正）。 |
| **VPK** | Valve 的打包格式，类似 zip。CS2 的模型、地图、材质都装在 VPK 里。 |
| **glTF** | 一种通用的 3D 模型文件格式（`.glb`/`.gltf`），Three.js、Blender 等都能读。把 CS2 的模型导成 glTF，就能在网页里渲染。 |
| **lightmap（光照贴图）** | 游戏预先"烤"好的光照结果，贴在场景表面上。有它才有真实的光影；没有它，模型看起来就是平的、塑料感的。 |
| **Animgraph** | Source 2 引擎的动画状态机系统。它决定"角色在跑动时应该播哪个动画、怎么混合"。**它不是一段可以导出的动画数据，而是一套运行时逻辑。** |
| **命中盒（hitbox）** | 游戏判定子弹打中哪里的隐形盒子（头、胸、腿各有各的盒子）。**它和看得见的模型是两套东西。** |
| **碰撞网格（collision mesh）** | 地图里"实际挡住玩家"的那层几何。它和你看到的墙面贴图是两套数据 —— 碰撞网格通常简单得多。 |

## 1. Demo 解析器 —— 把 `.dem` 读成程序能用的数据

这是整条链路的起点。你不必自己啃 demo 的二进制格式，用现成的库就行。

### 1.1 demoparser2 —— 最主流的选择（Python 能直接用）

**是什么**：核心用 Rust 写的 demo 解析器，外面套了一层 Python 接口，PyPI 上叫 `demoparser2`，`pip install demoparser2` 就能装。

**通俗说**：给它一个 `.dem` 文件，它把里面每一帧的游戏状态还原成表格，你用 pandas 就能处理。

**怎么用**（这些函数名就是它的公开接口，我逐个解释）：

| 函数 | 作用 |
|---|---|
| `parse_ticks(["X","Y","Z","health","yaw"])` | 最常用的一个。你**告诉它你要哪些属性**，它返回一张表：每行是「某个 tick 的某个玩家」，每列是你点名的那些属性。 |
| `parse_grenades()` | 返回所有投掷物（烟雾弹、燃烧瓶、闪光弹、手雷）逐 tick 的位置和状态。 |
| `parse_event("player_death")` | 返回某一类**事件**的列表。事件名要先查。 |
| `parse_skins()` | 本场出现的武器皮肤。 |
| `parse_player_info()` | 玩家信息（名字、SteamID、队伍）。 |
| `list_updated_fields()` | **最重要的一步**：问它「这份 demo 里到底有哪些属性可以用」。它返回一个字段清单（我这份是 **966 个**）。**一定要先调这个**，原因见下面"坑"。 |
| `list_game_events()` | 有哪些**事件类型**可以用。 |

**做不到什么**（我把 966 个字段**全量扫过一遍**，下面是精确结论）：

只剩 **2 类东西真取不到**：

1. **燃烧瓶 / 燃烧弹的火焰格子** —— `m_firePositions`、`m_fireCount`、`m_bFireIsBurning`、`m_fireParentPositions`、`m_nInfernoType`、`m_nFireLifetime`、`m_nFireEffectTickBegin`、`m_BurnNormal`。这几个名字在 `list_updated_fields()` 里**看得到**，但**两条取值路径都取不出来**。
2. **烟雾体素数据的"内容"** —— `m_VoxelFrameData` 这个数组本身。
   ⚠️ **必须分清**：它的**大小** `m_nVoxelFrameDataSize`（实测 `802`）和更新计数 `m_nVoxelUpdate` **是能取到的**；取不到的是那 802 字节的**内容** —— 在 demoparser2 里它退化成一个 **float64 标量**（不是数组），等于拿不到。

**还有一个最容易踩的坑：同一个属性，走不同的取值路径，结果完全不同。**

| 取值路径 | 投掷物属性能取到什么 |
|---|---|
| `parse_ticks(["Grenade.xxx"])` |  大部分**取不到**（静默丢弃） |
| `parse_grenades(extra=["xxx"])` | ✅ **能多取到 38 个** |

走 `parse_grenades(extra=[...])` **能取到**的（实测非空）包括：

```
m_vSmokeDetonationPos  m_vSmokeColor  m_nSmokeEffectTickBegin  m_bDidSmokeEffect
m_nVoxelFrameDataSize  m_nVoxelUpdate                       ← 烟雾 bloom 代理信号（内容取不到）
m_vInitialVelocity     m_vInitialPosition  m_flThrowStrength  ← 可重建真实弹道物理
m_nBounces             m_flDetonateTime    m_bIsIncGrenade     ← 真实弹跳次数 / 引爆时间
m_vecExplodeEffectOrigin  m_hThrower  m_bIsLive  m_flDamage  m_DmgRadius  ...
```

> **所以「`parse_ticks` 取不到」≠「demoparser2 取不到」。** 我第一次扫描时就是栽在这里 —— 用 `parse_ticks` 测出 81 个字段"丢弃"，换成 `parse_grenades(extra=...)` 后其中 **38 个其实拿得到**。真正的缺口只有上面那 2 类。

- **玩家操作指令**：实体属性层**有按键掩码**（见 §4.1），两个解析器都能取；packet 层还有更细的（见 §4.2）。
- 未知属性名**不报错，直接忽略** —— 这是最坑的地方。

> ⚠️ **实测踩过的坑（务必记住）**：如果你写了 `parse_ticks(["不存在的字段"])`，它**不会报错**，只会返回一个空表。我一开始就被这个骗了 —— 以为"字段不存在"，其实是"名字写错了但没告诉我"。**所以每次都要检查返回的列里到底有没有你要的东西。**

**实测数据**（我在这台机器上跑的）：
- 版本 **0.42.0**
- 一次拉取全量数据（31 个属性 × 167,846 个 tick × 10 个玩家 = **166 万行**）耗时 **7.32 秒**，内存峰值 **2.6 GB**（这是在已删除的 de_inferno demo 上测的）
- **同一份 `test.dem` 上的公平对比**（15 个属性 → 18 列，**101 万行**）：**7.33 秒**
- 只拉投掷物：**0.95 秒** / 229 万行

**许可**：**MIT** ✅（我打开 LICENSE 文件看过）
**平台**：全平台 ｜ **状态**：✅ 已实测

### 1.2 demoinfocs-golang —— 另一个独立实现，对烟雾和火焰有专门支持

**是什么**：一个用 Go 语言写的 demo 解析库，仓库是 `github.com/markus-wa/demoinfocs-golang`。和 demoparser2 是**两个独立项目**，走的技术路线不一样。

**通俗说**：目标一样（读 `.dem`），但设计思路不同 —— demoparser2 偏"给你一张大表，你自己筛"；demoinfocs 偏"**它认识游戏里的每种东西，做成了现成的对象给你遍历**"。

**它的特别之处**（这是我上一版写成"一等公民"、结果没人看懂的地方）：

游戏里的燃烧瓶烧起来后，地面上不是一整块火，而是**分散成一小片一小片**（最多 16 片）。别的解析器只给你一堆数字，你得自己猜"这堆坐标是不是火焰"。**demoinfocs 直接认识这些东西**，给了三个现成的东西：

| 接口 | 它到底给你什么 |
|---|---|
| `Infernos()` | 「**现在场上所有的燃烧瓶火焰**」。返回一个列表，每个元素代表一个正在烧的燃烧瓶。你遍历这个列表就能知道当前有几处在烧、各自烧了多久。 |
| `Fires().Active()` | 「**这一个燃烧瓶当前正在烧的那几小片火**」。返回每小片的中心坐标 `(x, y, z)`。也就是游戏真正在用的火焰格子位置。 |
| `ConvexHull2D()` | 「**把这些火点投影到水平面，连出外轮廓**」。给出一个二维多边形。⚠️ **注意"2D"是真的 2D** —— 它把 Z 轴丢掉了（见下面 §5.5）。 |

**为什么这个重要**：这三样东西是**游戏真正在用的数据**。你不需要自己发明一套火焰扩散模型去模拟"火大概会烧到哪里"，直接问游戏要就行。

**实测数据**（在这台机器上跑的，解析一份 de_ancient 的 `test.dem`）：
- 版本 **4.5.1**。**同一份 `test.dem`**：**5.36 秒**，**内存峰值仅 124 MB**（这个时间还包含了我额外的火焰格子分析 + 烟雾扫描开销，纯解析更快）
- **56 处火焰，每处都拿到完整的 16 片格子**（16 正好是 Valve 设定的上限）
- 拿到的真实坐标示例（一处平地上的火）：
  ```
  cell[ 0] (1295.4, -806.3,  4.2)      cell[ 8] (1202.2, -773.7,  3.9)
  cell[ 1] (1271.5, -833.5,  1.1)      cell[ 9] (1328.7, -880.9,  2.7)
  cell[ 2] (1247.0, -861.8,  1.8)      cell[10] (1316.2, -845.5,  1.4)
  ```
  这些位置是**真实散射的几何形状**，不是规则点阵 —— 说明是真数据。

⚠️ **一个坑**：这些格子**不是**一个叫 `m_firePositions` 的属性。Source 2 把定长数组**摊平成带下标的属性名**，所以要读的是 `m_firePositions.0000`、`m_firePositions.0001` ……（4 位补零）。**直接读 `m_firePositions` 会得到一个空数组**，很容易误判成"数据不存在"（我就先踩了一次，见 §5.5）。
- 还成功读出了**烟雾的体积数据原始字节**（`m_VoxelFrameData`），这是 demoparser2 拿不到的（见 §5）

**许可**：据调研是 **MIT**（我没有亲自打开 LICENSE 核对）
**平台**：全平台（Go 编译）｜ **状态**：✅ 已实测

> **和 demoparser2 的关系**：不是替代关系，各有各的强项。demoparser2 的 Python 接口更好用、生态更成熟；demoinfocs 能拿到投掷物的真实数据。**两边可以一起用**（比如用 demoinfocs 拿烟雾火焰，用 demoparser2 拿玩家轨迹）。

### 1.4 两者在同一份 demo 上的实测对比

为了公平，我在**同一个文件**（`test.dem`，de_ancient）上各跑一次：

| | demoparser2 | demoinfocs-golang |
|---|---|---|
| 耗时 | **7.33 秒** | **5.36 秒**（还含我额外的火焰/烟雾分析开销） |
| 内存峰值 | 物化 **101 万行** DataFrame（GB 级） | **124 MB** |
| 输出形态 | 一次性给你一张大表（pandas DataFrame） | 写回调逐帧处理，或自己攒结果 |
| 966 个字段里能取到 | **885** 个（走 `parse_ticks`） | 名义上全部，但要自己写取值代码 |
| 投掷物物理（初速 / 弹跳 / 引爆时间 / 烟雾颜色·引爆点） | ✅ **能取到**（走 `parse_grenades(extra=[...])`） | ✅ 能取到 |
| **火焰格子** `m_firePositions` 等 8 个 | ❌ **取不到** | ✅ **能取到** |
| **烟雾体素数组内容** `m_VoxelFrameData` |  只给一个标量 | ✅ **能取到完整数组**（实测 6145 个元素） |
| 火焰/烟雾的便利接口 | 无 | 有（`Infernos()` / `Fires().Active()` / `ConvexHull2D()`） |
| 用起来 | `pip install` 后直接写 Python | 要写 Go 代码、自己编译 |

> **所以「谁更好」取决于你怎么用**：demoinfocs 更快、更省内存、数据更全；但它是 Go 库，而 demoparser2 直接给你 pandas 表格。

### 1.5 该选哪个？

**结论：不是替代关系，demoparser2 仍然适合做主力。** 理由：

1. **它不是「设计更差」，是 `parse_ticks` 这条路径上有个具体的缺口。** demoinfocs 并不是解析得更对 —— 它只是**没有这个缺口**：`find_non_player_props()` 只处理"队伍/规则/时间"三类属性，grenade 属性归一化成 `Grenade.*` 后命中 `PropType::Weapon`，落到 `_ => vec![]` **被静默丢弃**。而 `parse_grenades(extra=[...])` 走的是**另一条代码路径**，所以能多取回 38 个（§1.1 表）。真正两条路径都拿不到的只有**火焰格子 + 烟雾体素内容**。修法就是给那个分支补一个匹配，改动很小。
2. **`Infernos()` / `ConvexHull2D()` 是便利封装，不是新数据。** 底层读的就是那 4 条带下标的属性（`m_firePositions.NNNN` / `m_BurnNormal.NNNN` / `m_fireParentPositions.NNNN` / `m_bFireIsBurning.NNNN`）。你拿到这 16 组值后，自己算外轮廓也就十来行代码。**注意 demoparser2 取不到它们（见 §5.4 A），所以这一块确实还是得走 demoinfocs 或打补丁。**
3. **有个成熟项目已经用脚投票了**：`CS2-Insight-Agent`（870★）**选择打补丁继续用 demoparser2，而不是换到 demoinfocs** —— 它用的就是自己编译的 demoparser2。
4. **Python 生态是硬优势**：直接出 DataFrame，能立刻进 pandas / numpy / torch 做特征工程和训练。改用 Go 意味着整条 AI 管线要么重写，要么多一层跨语言桥接。

**几种组合方式**：

| 情况 | 做法 |
|---|---|
| 管线是 Python（cs-net 就是） | **主力用 demoparser2**；只对「**火焰格子 + 烟雾体素内容**」这一件事，用 demoinfocs 补一条 Go 小工具导出 JSON/Parquet。投掷物物理直接走 `parse_grenades(extra=[...])`，不用第二个解析器 |
| 愿意动 Rust | **给 demoparser2 打补丁**（在 `find_non_player_props()` 里补那个匹配分支），之后**全程留在 Python**，连 Go 工具都不需要 |
| 本来就在写 Go / 不需要 pandas | 直接用 demoinfocs-golang |

**demoinfocs 反而更差的地方**（这几条我原来是漏的，实测后补上）：

| 项目 | 情况 |
|---|---|
| 眼位 `PositionEyes()` | ⚠️ **在 Source 2 demo 上直接 panic**（"not supported for Source 2 demos"）。想要眼位得自己用坐标 + 视角算。 |
| 手雷飞行轨迹 | ⚠️ **只有关键点，不是逐 tick**。实测 294 颗手雷共 **1618 个点、单颗最多 12 个**，但其中一颗的帧跨度是 **1953 帧**（30 秒）——平均 100 多帧才一个点，而且还出现相邻两点重合、以及 250 帧的空洞。**不能当逐 tick 轨迹用**；demoparser2 的 `parse_grenades()` 是逐 tick 的。 |
| 皮肤的 item def index / paint kit | ⚠️ 在**投掷物实体上读不到**（在武器实体上才有）；demoparser2 反而能从 `Grenade.*` 读到。 |
| 取值方式 | ⚠️ **单次顺序流式解析**，不能像 `parse_ticks(ticks=[...])` 那样按需只取某几个 tick。你要什么就一遍全吐出来。 |

**推荐架构（结论）**：**demoparser2 当主力，demoinfocs 只补一个极窄的口子。**

| 部分 | 用什么 | 为什么 |
|---|---|---|
| 玩家逐 tick 状态、13 个事件、投掷物逐 tick 轨迹、按键掩码 | **demoparser2** | 直接出 pandas DataFrame，能立刻进 numpy/torch；覆盖完整 |
| **火焰 16 格几何** + **烟雾体素内容** | **demoinfocs 写一个小导出器** | 这是唯一两条路径都拿不到的东西（§5.4） |

**两条替代路线，以及为什么先不选**：

| 路线 | 代价 | 判断 |
|---|---|---|
| **给 demoparser2 打补丁**（补上 grenade/inferno 那一组） | 要自己维护一个 Rust fork；我已定位到**事件路径**的缺口在 `find_non_player_props()` 的 `_ => vec![]`（`second_pass/game_events.rs:307`），但**`parse_ticks` 那条路径的改动量我还没核实** | **是更好的终点状态**，但没核实前不该承诺"很小"。好处是彻底不用第二个解析器 |
| **整体换成 demoinfocs** | 丢掉 pandas 生态；且它自己有 3 处退化（手雷轨迹只有关键点、`PositionEyes()` panic、不能按需取 tick） |  不推荐 |

**补丁式的成本其实很低**，有两个可以省掉大量开销的点：

1. **烟雾体素不需要逐 tick 导出** —— 它是**只追加的日志**，所以**每颗烟只导出一次最大日志**，再用逐 tick 的 `m_nVoxelFrameDataSize` / `m_nVoxelUpdate` 两条整数曲线去**切前缀**，就能还原任意 tick 的体积。曲线本身只是每 tick 两个整数。
2. **火焰不需要逐 tick 导出** —— `m_fireCount` 一次燃烧里只变化 **约 10 次**（实测 1→16 的台阶），所以导出**每次变化时的快照**即可。

⇒ 每条 demo 的额外产物大约只有：**56 处火焰 × 约 10 个快照 × 16 格** + **81 颗烟 × 1 份日志（中位 2.5 KB）** —— 量级很小，可以一次性算完缓存。

⚠️ **要付的代价**：同一份 demo 要**解析两遍**（实测 demoparser2 7.33 s + demoinfocs 5.36 s）。做几千份 demo 的数据集时这是实打实的开销 —— 这正是"打补丁"路线在规模化后更优的原因。

**验证状态**：这次我把 demoparser2 的 **966 个字段全量扫了一遍**，"能取 / 取不到"以及"换路径能不能取到"都是实测的；demoinfocs 这边则**逐项核对了我现在管线真正在用的字段**（见 §1.6）。**我仍然没有验证过 demoinfocs 的全部事件类型和队伍/规则类属性**，所以**仍不建议整体切换** —— 补一个分支的风险还是小得多。

## 2. 资产提取 —— 从 VPK 里把模型、地图、材质挖出来

CS2 的模型和地图都打包在 **VPK** 文件里（见名词解释）。要用它们，先得解包、转成通用格式。

### 2.1 ValveResourceFormat / Source2Viewer-CLI

**是什么**：Valve 自己文件格式的**事实标准**解析工具。有命令行版（`Source2Viewer-CLI`）和图形界面版（Source2Viewer）。社区维护，是目前唯一能比较完整读 Source 2 资源的开源工具。

**通俗说**：它能把 CS2 的模型文件（`.vmdl`）和地图文件（`.vmap`）**转换成通用的 3D 格式 glTF**，这样 Three.js、Blender 之类都能直接打开。它也能列出 VPK 里都有什么文件。

**怎么用**：
```
# 列出 VPK 里有哪些模型文件
Source2Viewer-CLI -i pak01_dir.vpk --vpk_list -f "agents/models/" -e vmdl_c

# 把某个模型导出成 glTF
Source2Viewer-CLI -i xxx.vmdl_c -o out/ --gltf_export_format glb
```

**导出的 glTF 里有什么**：模型的网格、材质、骨骼（骨架）、动画剪辑。

**做不到什么（这是重点，别期待落空）**：

| 缺什么 | 后果 |
|---|---|
| **没有 lightmap（光照贴图）** | 导出来的模型是"素"的，没有游戏里那种光影。想好看得自己重新打光。 |
| **没有点光源/聚光灯** | 地图里的灯光不会跟着导出。 |
| **没有粒子系统** | 烟雾、火焰、火花这些**全是粒子效果，完全不会导出**。 |
| **没有 3D 天空盒**（已知问题 #967） | 天空是空的。 |
| **材质层会合并塌陷**（已知问题 #1161） | CS2 材质可以多层叠加（比如磨损、贴花），导出后会丢掉层次。 |
| **Animgraph 从不被执行** | 这是最容易被误解的一条：你会得到"一段段动画剪辑"，但**没有得到"角色在跑动时该播哪一段"的逻辑**。那套逻辑是引擎运行时算的，导不出来。你得自己在网页里写一套动画状态机。 |
| **没有命中盒** | 游戏判定子弹的隐形盒子不在导出结果里。它和可见模型是两套数据。 |
| **人物模型有蒙皮 bug**（已知问题 #845 `Invalid skinning bone index`） | 骨骼绑定可能出错，模型会扭曲。 |

**许可**：据调研是 **MIT**（未亲自核对 LICENSE）
**平台**：全平台（.NET）｜ **状态**：📖 本机有 v19.2.6339 在 `~/Downloads/Source2Viewer-CLI/`，但没实际跑过导出

> 顺带一提，CS2 的模型路径是 `agents/models/<系列>/<文件名>.vmdl`。**注意 `models/players/` 这个路径在 CS2 里不存在**（那是 CS:GO 时代的）。默认 CT 模型是 `ctm_sas`，T 是 `tm_phoenix`。动画名字带武器后缀，比如 `idle_knife`、`run_n_knife` —— **裸的 `idle`、`run`、`death` 是不存在的**，这点很容易踩坑。

### 2.2 ValveResourceFormat.Renderer

**是什么**：VRF 项目里的一个**渲染器**组件（.NET 10 + OpenGL）。和上面那个"导出器"是两回事。

**通俗说**：上面那个是把资源**导出成文件**，这个是**直接在程序里把资源画出来**，不经过 glTF 中转。理论上保真度更高（因为不丢信息），但它是 .NET 桌面程序，不是给你在网页里用的。

**许可**：据调研 MIT ｜ **状态**：📖

**是什么**：Steam 逆向社区（SteamRE）做的工具，能从 Steam 服务器**选择性下载**游戏的某一部分。

## 4. 玩家操作输入 —— 拿到"玩家当时按了什么键"

**先说背景**，因为这里有个我一开始搞错的地方：

demo 里其实有**三层**不同的数据：
1. **实体属性表** —— 每 tick 的坐标、血量等等（§1 那些解析器读的就是这层）
2. **游戏事件** —— 「有人开枪了」这类离散事件
3. **网络消息（packet 层）** —— 服务器发给客户端的数据包原文

玩家的**按键操作**在哪一层？我一开始的结论是"在第 3 层"—— **这个结论只对了一半**：完整的按键掩码其实**第 1 层就有**（见 §4.1），第 3 层额外提供的是**鼠标**（见 §4.2）。我第一次找的时候还犯了个更基础的错：用了 `usercmd_mouse_dx`、`buttons` 这类**短名字**去查，而 demoparser2 的真实词汇表是**全限定名**（形如 `CCSPlayerPawn.CCSPlayer_MovementServices.m_nButtonDownMaskPrev`），短名字会被静默丢弃，于是我把"名字写错"误判成了"数据不存在"。

### 4.1 好消息：实体属性层**本来就有按键掩码**（两个解析器都能取）

我原来以为按键只在第 3 层，后来实测发现**第 1 层就有一个**：玩家实体上的 `m_nButtonDownMaskPrev`，是一个 64 位整数，**每一位代表一个键**。

| | 取的写法 |
|---|---|
| demoparser2 | `parse_ticks(["CCSPlayerPawn.CCSPlayer_MovementServices.m_nButtonDownMaskPrev"])` |
| demoinfocs-golang | `Player.ButtonsPressedState`（或原始属性同名） |

**实测：两边的数值逐位完全一致。** 我拿 60 组 `(tick, steamid)` 对照，能对上的 54 组**一个不一致都没有**（剩下 6 组是 demoinfocs 的出场名单里当时没这个人，值都是 0）。

**这 13 个键在第 1 层全都有**（我把整份 demo 的所有掩码按位或起来，逐位统计）：

| 键 | 位 | 整份 demo 里被按下的行数 |
|---|---|---|
| W（前） | `0x8` | 390,069 |
| D（右） | `0x400` | 135,370 |
| A（左） | `0x200` | 133,592 |
| walk（走） | `0x10000` | 120,488 |
| fire（开火） | `0x1` | 85,328 |
| scoreboard | `0x200000000` | 59,708 |
| S（后） | `0x10` | 34,999 |
| crouch（蹲） | `0x4` | 28,399 |
| scope（开镜） | `0x800`（Attack2） | 18,903 |
| inspect（检视） | `0x800000000` | 8,602 |
| jump（跳） | `0x2` | 5,049 |
| use（用） | `0x20` | 4,990 |

**结论：只想要「按了哪些键」，第 1 层（实体属性表）就够了，两个解析器都能直接拿到，不需要碰第 3 层。**

### 4.2 第 3 层（packet）额外能拿到什么：`svc_UserCmds`


**是什么**：CS2-Insight-Agent 项目里的一个 **Rust 二进制程序**，专门解 `svc_UserCmds` 这条网络消息。

**通俗说**：它把 demo 里"玩家按了什么键"解出来。CS2 服务器每秒 64 次收到每个玩家的操作指令，这些指令**原样存在 demo 里**。

**它能解出什么**：**13 个按键**，用位掩码表示（一个整数的每一位代表一个键）：

```
W  A  S  D  jump  crouch  walk  reload  fire  scope  use  inspect  scoreboard
```

**输出格式**：一串紧凑的增量编码（形如 `"tickDelta.mask"` 的 base36 字符串），表示"过了多少 tick 之后按键状态变成了什么"。这样一条 13 键的完整时间线能压得很小。

**它还做了哪些可靠性设计**（说明这条通道是认真的，不是猜的）：
- 有**完整性契约**：`format_version >= 10`，而且 `decode_errors == 0`、`commands_without_player_slot == 0` 才接受结果，否则直接报错
- 用**玩家身份时间线**（`player_identity_updates`）把"第几个位置"绑定到"哪个 SteamID"，所以比赛中间换人也能正确处理

**做不到什么**：
- **只有按键，没有鼠标位移和转向**。公开代码里列的就是这 13 个键。（视角可以从实体属性表的 `view_angle`/`angles` 拿，那层是能读的。）
- 我**没有实际运行验证过** —— 它是 Windows 专用的，而且需要先编译那个 Rust 二进制。

**许可**：**PolyForm Noncommercial 1.0.0** ✅（我读过它的 README）
**平台**：Windows ｜ **状态**：📖 只读了实现，未运行

## 5. 烟雾体积数据 —— 把 CS2 的烟雾真正"解"出来

这是这次调研里最有意思的一块，也解释了我之前为什么反复搞错。

### 5.1 背景：烟雾的体积数据到底长什么样

CS2 的烟雾不只是一个球。服务器**真的在算一个三维的体素（小方块）网格**，记录"这一小块空气里有多少烟"，然后把这份数据发给客户端去渲染。

这份数据存在属性 `m_VoxelFrameData` 里。我一开始拿到它时，看到 3072 个字节，就理所当然地以为"这是个 16×16×12 的三维网格"——**错了两次**：

- 第一次：我说"3072 个格子的密度值"。错。
- 第二次：我说"它不是规则网格，所以解不出来"。也错。

**真相是：它根本不是一张静止的网格，而是一条经过压缩的"录像带"。**

> **谁能拿到这条"录像带"？**（§1.1 的结论在这里最关键）
>
> | | demoparser2 | demoinfocs-golang |
> |---|---|---|
> | `m_nVoxelFrameDataSize`（录像带**有多少字节**） | ✅ 能取（实测 `802`） | ✅ 能取 |
> | `m_nVoxelUpdate`（更新计数） | ✅ 能取 | ✅ 能取 |
> | **`m_VoxelFrameData`（录像带**内容**）** | ❌ **只给一个 float64 标量** | ✅ **完整数组**（实测 6145 个元素） |
>
> ⚠️ 注意 demoparser2 里 `parse_grenades(extra=["m_VoxelFrameData"])` **会返回一列、不会报错**，但那一列是**标量不是数组** —— 这正是"列存在 ≠ 数据正确"的典型陷阱。

### 5.2 CS2-Insight-Agent 的 `smoke_voxel_decode.py`

**是什么**：这个项目里公开的一份 Python 代码，把上面那条"录像带"解开了。

**通俗说**：`m_VoxelFrameData` 不是"一张三维网格图"，而是**一串按时间排列的记录**，就像视频用的是"第一帧完整画面 + 后续只记录变化的部分"：

| 记录类型 | 含义 |
|---|---|
| **关键帧（type 3）** | 完整描述："烟雾是这些格子"。包含一批种子点位 + 一批掩码。 |
| **增量帧（type 2）** | 只描述变化："把这几格改成这样"。 |
| **心跳帧（type 0）** | "这一帧没变化"。 |

每一条记录前面有 4 个字节的头：序号 + 数据长度。

**那 3072 个字节里我当成"密度"的东西是什么？** 其实是**结构信息** —— 长度字段、帧类型、种子数量。这就是我前两次判断错的原因：我拿结构字节当密度去做空间分析，当然得不出东西。

**真正的三维信息怎么存的**（这里用到名词解释里的 Morton 编码）：

- 网格是 **32 × 32 × 32**
- 但不会老老实实存 32768 个数。它分两级压缩：
  - 先切成 **8×8×8 = 512 个大格子**，每个大格子的编号用 Morton 编码压成一个小整数
  - 每个大格子配一个 **64 位的掩码**，每一位代表它内部 4×4×4 = 64 个小格子中有没有烟
- 所以"哪些地方有烟"就是一批「大格子编号 + 64 位掩码」
- 掩码描述的是**烟雾的表面边界**；被边界围住的内部，本来打算用**洪泛填充**（从外表面往里推）算出来

> **⚠️ 2024 后续更正**：洪泛填充在真实数据上**失效**。掩码虽然描述表面，但采样很稀
> （平均每 (x,y) 列只有 ~4 个 Z，没有一个格子的 64 位全满），空腔和外界是连通的，
> 从六个外表面推进去**一个内部体素都补不出来**（82 个烟里 59 个增益为 0）。
> 想要实心云得改成**填满表面点云的凸包**（`tools/demo_extract/voxel.py` 的
> `solid_from_shell` / `convex_hull_fill`）。凸包没有任何可调参数，代价是它假设
> 烟雾是凸的 —— 真实的凹陷会被一并填平。详见 `tools/demo_extract/README.md` §6。
>
> 顺带说明：**这些几何重建都只是读取端/渲染端的事**，`.csz` 里存的始终是原始
> journal 与真实火焰格子，改 `solid_from_shell` 不会动到数据文件一个字节。

**怎么换算成游戏里的坐标**：

```
世界坐标 = 引爆点 + (网格坐标 − 15.5) × 12
```

### 5.5 火焰数据长什么样 —— 它**不是平面**

"火焰格子"这名字容易让人以为是一层平铺在地面上的方格。**实测下来不是**：一个燃烧瓶烧出来的 16 片火，可以**从地面一路爬上去 124 HU（约 2.4 米）**，每片火的朝向还各不相同。

#### 一个燃烧瓶到底记了什么

对每处火焰（`CInferno` 实体）有 **4 条并行的数组**，长度都是 `m_fireCount`（1 → 最多 16）：

| 属性（注意要带下标） | 含义 |
|---|---|
| `m_firePositions.NNNN` | 第 i 片火的**三维世界坐标** |
| `m_BurnNormal.NNNN` | 第 i 片火所在**表面的朝向**（单位法向量） |
| `m_fireParentPositions.NNNN` | 第 i 片火是**从哪一片烧过来的**（父节点；第 0 片的父节点是它自己） |
| `m_bFireIsBurning.NNNN` | 第 i 片现在**还在烧吗** |

> 读法：`m_firePositions.0000`，**4 位补零**。读不带下标的 `m_firePositions` 只会拿到空数组。

**`m_fireParentPositions` 是"蔓延树"**：它记录了火是从哪一格蔓延到哪一格的，也就是**火的传播路径和方向**。第 0 片是起点（父节点 = 自己）。这是免费的扩散图。

#### 实测：火焰到底有多不平（56 处火焰，`test.dem`）

| 指标 | 实测 |
|---|---|
| 每处的格子数 | **全部 16**（56/56）；但 `m_fireCount` 在燃烧过程中**从 1 涨到 16**（56/56 都在变） |
| 蔓延耗时 | 例：一处 **13 tick（0.2 秒）** 铺满，另一处 **91 tick（1.4 秒）** |
| **垂直跨度 dZ** | 最小 2.5、最大 **124.3 HU**（≈2.4 m） |
| **平面拟合残差** | 最大 **53.5 HU**（若真是平面，这个值应接近 0） |
| 落在水平面上的火（dZ < 10 HU） | **17/56（30%）** |
| 明显在爬升的火（dZ > 50 HU） | **6/56（11%）** |
| **法向量明显倾斜**（nz < 0.9，即偏离竖直 > 25°） | **21/56（37.5%）** |
| 最斜的法向量 | nz = **0.117**（≈83°，几乎是**竖直的墙面**） |
| 已熄灭的格子（`m_bFireIsBurning=false`） | 896 格里只有 **6 格** |

#### 两个真实例子

**① 平地上的火**（残差 2.9 HU）—— 法向量几乎全是竖直向上，Z 只在 1.1～5.6 之间：

```
   [ 0] (1295.4 -806.3   4.2)  parent=(1295.4 -806.3   4.2)  normal=(0.003 -0.238 0.971)
   [ 1] (1271.5 -833.5   1.1)  parent=(1295.4 -806.3   4.2)  normal=(0.003 -0.036 0.999)
   [ 9] (1328.7 -880.9   2.7)  parent=(1279.3 -868.2   2.4)  normal=(0.144  0.022 0.989)
```
> `m_fireParentPositions` 在这里是一棵**分叉的树**：1 号从 0 号烧来，2 号从 1 号烧来，4 号又回到从 1 号烧来……

**② 爬升的火**（同一处的 16 格，Z 从 218 爬到 343，跨 124 HU）—— 法向量从"平"到"很斜"全都有：

```
   [ 7] ( 326.9 1009.1 218.8)  normal=( 0.019  0.078 0.997)   ← 平地
   [ 2] ( 385.4 1142.7 300.6)  normal=(-0.121 -0.790 0.601)   ← 斜约 53°
   [ 9] ( 520.3 1098.7 240.4)  normal=(-0.140 -0.913 0.384)   ← 斜约 67°
   [11] ( 487.9 1158.4 342.6)  parent=(507.1 1114.3 259.9)    ← 最高的那格
```
> 注意法向量的**方向也不同**（有的偏 −Y、有的接近竖直），说明火是**贴着不同朝向的表面**铺开的，不是铺在一个斜面上。

#### 结论：不要用 `ConvexHull2D` 当火焰体积

- `ConvexHull2D()` 是**投影到水平面的二维轮廓** —— 对"玩家能不能走过去"这种地面封锁判断够用，但**它把上面那 124 HU 的爬升整个丢掉了**。
- 如果要做 **3D 占据栅格**（AI 训练需要的空间表示），正确的输入是：
  **`m_firePositions`（三维点）+ `m_BurnNormal`（每点的表面朝向）+ `m_fireParentPositions`（蔓延树）+ `m_bFireIsBurning`（是否在烧）**。
- 我上一轮在 PLAN 里写"16 格坐标 + `ConvexHull2D` 直接给出封锁区域"—— **那是个偷懒的简化，低估了这份数据的维度**。

> 复现脚本：`notes/scratch/fireprobe/main.go`（`summary` / `raw` / `count` 三种模式）

### 平台方面的硬约束（已核实）

- **CS2 根本没有 macOS 版**。Steam 的元数据里 `platforms.mac=false`；macOS 对应的 depot（`2347772`）只有 **约 9 KB**，就是个空壳。**所以这台 Mac 上不可能做 CS2 的引擎内渲染**，跟工具无关。
- CS2 的 Windows 客户端**装完约 71.6 GB**（下载约 59.9 GB，Valve 官方标称需要 85 GB 空间）。
- CS:GO 的老版本（Steam app `4465480`）是 **Windows + Linux**（元数据 `mac: false`）。它的运行配置里确实有 macOS 的痕迹（有个 `csgo.sh` 启动项、`validoslist` 里写了 macos、macOS depot `733` 有 277 MB），但**最可能只是 CS:GO 当年还有 Mac 版时留下的陈旧元数据**，不代表现在能装。
- 这台机器目前可用磁盘 **29 GB**。

## 9. 引擎内渲染（云端服务）—— 不装游戏也能拿到真游戏画面

### 9.1 DEMO-SLAP —— 有 API 的云端真引擎渲染

**是什么**：一个在线服务，你上传 demo 或给个链接，**它在自己的机器上真的启动 CS2**，把指定时间段渲染成 mp4 发给你。

**通俗说**：你不需要装游戏、不需要 Windows、不需要显卡，付钱就能拿到真游戏画面。

**怎么用**（它有标准的 **OpenAPI 3.0** 接口文档）：
```
POST /analyze/url          → 提交 demo，返回 jobId
GET  /analyze/{jobId}/data → 拿分析结果
POST /render-custom/{jobId}→ 指定 tick 区间 + 指定玩家视角（povSteamId），出片
GET  /render/{jobId}       → 普通出片
```
鉴权用 `x-api-key`。还提供 MCP connector。

**它确实是真引擎**（证据）：选项里有 `hideUi`、`showXRay`、`showTracers`、`hideKillfeed`、`hideWatermark` 这些游戏内开关；分析接口的 `source` 参数里有个值叫 `rungame-url`，说明它真的在跑游戏。

**价格**：**约 €0.02–0.06 / 10 秒片段**（基础 0.1 点/秒，1080p 乘 1.5，去水印乘 1.5）。**每天送 17 个免费点**。

**注意事项**：
- 产出是**POV 风格的第一人称片段，不是自由机位的电影镜头**
- ⚠️ 这是个**两个人的瑞士副业项目**（他们自述"渲染机器放在我们家里"），属于**原型级**，不要指望生产级稳定性
